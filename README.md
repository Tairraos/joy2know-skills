# 晓得 · joy2know

**WorkBuddy 开放平台资产包仓库** —— 15 个技能（Skill）、2 个单专家、2 个专家团。

母品牌「晓得」，口号「一目晓得」。中文展示名写在 `display_name`（晓得·讲明白）；**凡需要英文名的位置，「晓得」与「晓得乐」一律译作 `joy2know`** —— 技能看 `display_name_en`，专家看 `profession.en` / `displayName.en`，包名与引用路径同样走 `joy2know-xxx`。
**触发匹配完全靠 `description`，`name` 不参与触发。**

- 作者署名：晓得乐 / joy2know
- 许可协议：**CC BY 4.0**（署名 4.0 国际）—— 可自由转载、改编、商用，**惟须署名**。全文见 [`LICENSE`](LICENSE)
- 归档目录 `private/` 记录的是这批资产的完整诞生过程（提示词 → 回答 → 产物）

## 目录结构

```

├── AGENT.md                ★ 工作手册：发布流程 + 发布前检测四道门（AI 和人共用）
├── docs/平台资产规范.md      ★ 完整规范手册：字段 / 结构 / 体积 / 类目 / 许可（原个人技能知识，已固化进仓库）
├── release.config.json     ★ 发布参考单一真源：逐包建议发布类目 + 平台侧最后版本
├── 发布清单.md             ★ 待上传产物一览 + 发布历史（前四节构建时自动重写，末两节人工维护）
├── packages/               ★ 资产包源文件（一个包一个目录，共 19 个）
│   ├── <包名>/skills.json     专家/专家团才有：声明内嵌哪些技能（构建时复制）
│   └── <包名>/<包名>.md       发布前检测报告 —— 开发期文档，**不进 zip**，但进 git
├── avatars/                ★ 图标统一管理（技能 + 专家 + 团队成员，打包时自动注入）
├── dist/                   产物 zip（pnpm build 生成，已 gitignore）
│   └── <包名>-v<版本>.zip     带版本号的发布包（同包只留最新一版）
├── scripts/
│   ├── build.mjs           打包工具
│   ├── selfcheck.py        四道字段自检（**仓库自带，不再依赖本机技能目录**）
│   ├── init-checkdocs.mjs  生成检测报告骨架
│   ├── placeholders.py     图标占位图
│   ├── shrink-icons.py     图标规格体检
│   └── make-avatar.py      零积分画头像
├── private/               阶段归档：流水文档 + 13 份产物 HTML/MD
├── README.md
└── package.json
```

三处分离的用意：**源文件不重复、图标不散落、产物不入库**。

> **本仓库自给自足**：自检脚本、字段规范、打包工具都在仓库里。换一台机器、换一个
> harness 克隆下来就能产出能过平台校验的包，**不依赖任何本机技能目录**。
> 操作流程看 `AGENT.md`，字段口径看 `docs/平台资产规范.md`。

## 快速开始

```bash
pnpm build                    # 打包 packages/ 下全部包 → dist/<包名>-v<版本>.zip
pnpm build joy2know-mr        # 只打包指定包（可给多个，支持前缀匹配）
pnpm run list                 # 列出全部包、版本、类型、图标状态与内嵌技能
pnpm run checkdocs            # 查看各包发布前检测报告的状态（缺的补骨架）
python3 scripts/selfcheck.py packages/joy2know-mr   # 单独跑字段自检（不打包）
```

> `pnpm run list` 要带上 `run` —— 裸写 `pnpm list` 会被 pnpm 自带的「列依赖」命令截走。

| 选项 | 作用 |
|---|---|
| `--no-check` | 跳过深度自检（selfcheck.py） |
| `--strict` | 深度自检有问题、或发布前检测报告未通过 / 版本不符，即中止（默认仅告警） |
| `--force` | 即使有错误也写出 zip |
| `--no-skill-icons` | 不把技能图标写进内嵌技能目录 |
| `--keep-old-zips` | 保留 `dist/` 里同包的旧版本 zip（默认清理，只留本次构建的那一版） |
| `--no-manifest` | 不重写仓库根的 `发布清单.md` |
| `--help` | 帮助 |

**依赖**：Node ≥ 18、系统 `zip` / `unzip`（macOS、Linux 自带）。**不引入任何 npm 依赖**，`pnpm install` 都不用跑。

打包时工具会自动做这几件事：复制内嵌技能（自动剔除被内嵌技能自己的检测报告）→ 从 `avatars/` 注入图标 → 校验图标规格与 zip 体积 → 确认 zip 第一层是包目录本身 → 检查发布前检测报告（缺 / 未通过 / 版本不符 / 比源码旧都会告警）→ 调 `scripts/selfcheck.py` 做深度自检 → **排除包内的检测报告** → 通过后才写入 `dist/` → 清理同包旧产物 → 清理 `dist/` 里遗留的旧位置清单 → 重写仓库根 `发布清单.md` 的自动区。**源目录始终不被改动。**

## 内嵌技能：构建时才复制，仓库内零副本

专家 / 专家团包要用某个技能时，**包里不放副本**，只在包根放一个描述文件 `skills.json`：

```json
// packages/joy2know-mr/skills.json
{ "skills": ["joy2know-clarify"] }
```

构建时工具会：

1. 从 `packages/joy2know-clarify/` 复制**真实技能**到暂存目录的 `skills/joy2know-clarify/`；
2. 按 `skills.json` **重写包内 `plugin.json` 的 `skills` 数组** —— 两处不一致会告警并纠回；
3. 把 `skills.json` 本身排除在 zip 之外；
4. 若源包里还残留 `skills/` 副本，直接弃用并按描述文件重建。

当前 9 处引用（去重后 8 个技能）：

| 包 | 内嵌技能 |
|---|---|
| `joy2know-mr` | `joy2know-clarify` |
| `joy2know-code-scholar` | `joy2know-codebase` |
| `joy2know-cine-team` | `joy2know-storyboard`、`joy2know-character`、`joy2know-musician` |
| `joy2know-polish-team` | `joy2know-clarify`、`joy2know-humanize`、`joy2know-deck`、`joy2know-dashboard` |
| `joy2know-promo-team` | `joy2know-clarify`、`joy2know-humanize`、`joy2know-dashboard` |

> 同一个技能可以被多个包内嵌（如 `joy2know-clarify` 同时在 `mr` 与 `polish-team` 里）—— 构建时各自从唯一真源复制，不产生副本。

**要改规则，只改 `packages/<技能名>/` 那一份。** 不用再手工 `cp`，也不会出现「两份文本漂成两套口径」。

## 图标统一管理

图标**只放 `avatars/`，源包里不放**。三类图标，按名字对应：

| 归属 | 放法 | 构建时去向 |
|---|---|---|
| **专家 / 专家团自身** | `avatars/<包名>.png` | 写到该包 `plugin.json` 里 `avatar` 字段指定的路径（如 `avatars/team.png`） |
| **专家团成员** | `avatars/<包名>/<文件名>.png` | 按**文件名**逐个写入包的 `avatars/`，文件名须与 `members[].avatar` 逐字对应 |
| **技能** | `avatars/<技能名>.png` | ①独立技能包**不注入**（官方技能包没有图标槽位，该图用于后台发布技能时上传）②被内嵌进专家包时复制为 `skills/<技能名>/icon.png` |

**规格：512×512、PNG、单张 ≤500KB。** 尺寸或格式不符会告警，体积超限直接报错。缺图标时该包仍会打包，但会明确告警。

### 缺图了用脚本补，别手画

```bash
python3 scripts/placeholders.py --check   # 缺哪些 · 哪些还是占位图 · 哪些已换成真图
python3 scripts/placeholders.py           # 补齐缺失的 512×512 占位图（绝不覆盖已有文件）
```

占位图是浅灰相框 + 太阳 + 山形，**底部印着「谁 · 待替换」**（`polish-lead.png` 上写着「闻山 / 主理人·总编审 · 待替换」）——
文件名只说得出 `polish-lead`，图上那句才说得清该画谁。有真图了直接覆盖同名文件即可。

脚本每次生成都会把 sha1 记进 `avatars/.placeholders.json`，所以 `--check` 能准确报出
「还剩几张没换」—— 替换是覆盖同名文件，光看文件在不在没用，得比内容。详见 `avatars/README.md`。

### 技能发布类目（平台按内容判定，须照选）

技能包内**没有**类目字段 —— 类目是发布时在**后台下拉框里选的**，选错会被打回：
「所选类目与应用类目不符，请重新选择相符类目，至少应包含 ……」。
其中「应用类目」是平台**按技能内容判定**出来的，「所选类目」是发布人手选的。**看平台给的提示照选，不要凭技能名猜。**

| 技能 | 平台判定的类目 | 依据 |
|---|---|---|
| `joy2know-asset-ledger` | **工具 > 图片处理** | 2026-09-23 首次提交被打回，理由原文：「至少应包含工具 > 图片处理类目」 |
| `joy2know-musician` | ⚠️ **深度合成 > AI创作** —— **但这一类目选不了**（只对企业开发者开放） | 2026-09-28 被打回，驳回原文见下 |

- 打回的措辞是「**至少应包含**」，说明该类目选择项**可能允许多选** —— 命中项之外可再补一个近义类目，别只勾一个。
- **类目选错只影响审核，与包本身无关** —— 改类目重新提交即可。⚠️ **但版本号必须抬**
  （「所选类目与应用类目不符」是**提交成功之后**的审核驳回，版本号已被平台占用 —— 见维护纪律第 19 条）。
- ⚠️ **例外：被判「深度合成」时不能照选。** 该类目**只对企业开发者开放**（个人主体需先企业认证），
  **这类驳回改类目解决不了，只能改应用本身** —— 说明字段只讲产出的是**文本**、不写第三方 AI 服务的
  档位与型号、触发词收回到「写作要求词」、并加一段显式「无深度合成」声明（正文设「定位与边界」节）。
  做法与边界见 `docs/平台资产规范.md` 第八节；本轮实例见 `packages/joy2know-musician/joy2know-musician.md` 的 2.8 节。

  **这一轮的结果仍然是实验** —— 平台判定「应用类目」究竟看说明字段还是整包内容，仍未实证。
- 其余技能首次提交时，同样**先看平台给出的判定提示再选**。

## 更新日志

> **自 2026-09-17 起记录。** 此前的变更没有留存，不再追补。
>
> **版本口径**：内容有实质改动 → patch（1.0.0 → 1.0.1）；新增能力、规则或角色 → minor（1.0.0 → 1.1.0）；字段或包结构改动 → major。
> **【本地升级】**标记 = 版本号已在本仓库抬高，而平台侧**还没有这个版本**（无论「还没提交」还是「提交了还在审」）。
> **三态口径（2026-09-25 定，与上一节表格一致）**：**① 开发完待提交** = 只在本地；
> **② 提交完待审核** = 已交平台、审核中，**只有开发者账号的发布管理页可见，接口读不到**；
> **③ 审核完成** = 已上架、用户端可见。**③ 能自动读，② 不能。**
> **这条是血的教训**：「市场里显示 1.1.0」只说明**最后过审的是 1.1.0**，**不代表没提交新版本**。
> **而且反过来也成立** —— 「有人跟我说交过了」同样不等于交过了：
> 2026-09-25 先据口头汇总记成「1.2 批 17 个包已提交」，当天用开发者页截图核对，
> **实际只有 8 个包在审**（技能 5 · 专家 1 · 专家团 2），8 个技能从未提交 1.2.0。
> **结论：② 只认发布管理页，任何二手汇总都要回页面核。**
> **③ 的读法**：用「推荐市场」按关键词检索，返回的 `version` 即最后过审在架的版本，**只覆盖技能**；

## 发布前检测：打包之前必须过四道门

**⛔ 硬规矩：没过发布前检测，不许打包上传。** 完整流程见 [`AGENT.md`](AGENT.md)，这里只说机制。

每个包在 **`packages/<包名>/<包名>.md`** 有一份检测报告（与包目录同名）。它有两个特点：

- **不进 zip** —— 构建时自动排除（被内嵌技能的那份也一并剔除），它纯属开发期文档
- **进 git** —— 要能看历史，也要让下一次检测先读它

报告头部有四行是**构建脚本用来判门禁的**，格式不能改：

```md
- **对应版本**：1.2.0
- **检测状态**：⚠️ 有条件通过
- **最后检测**：2026-09-23
- **检测方式**：功能测试 + 完整性对照 + 合理性检查 + 反向验证
```

| 状态 | 含义 | 能否打包 |
|---|---|---|
| `✅ 已通过` | 四道门全过，无遗留未覆盖项 | ✅ |
| `⚠️ 有条件通过` | 四道门已过，但存在明确的未覆盖项 | ✅（未覆盖项要写清） |
| `⛔ 未检测` | 还没测，或只有骨架 | ❌ 构建告警；`--strict` 失败 |
| `❌ 未通过` | 有硬缺陷未修完 | ❌ 构建告警；`--strict` 失败 |

四道门：**① 功能测试（真跑）② 完整性对照（文档承诺逐条核实现）③ 合理性（边界 / 降级 / 自洽 / 零依赖）④ 测试真实性（防假测试）**。
第四道门专门防放水，列了七种假测试形态（只跑 happy path、只看没报错、把「文档写了」当「已验证」、自造理想样本、
跳过失败项、不跑回归、造错样本只造会被抓的那种），并要求**反向验证**：改完校验器要故意造错样本，确认仍然抓得住。

**报告是给下一次的自己省时间用的。** 下次检测先读它：已验证且未变的部分可以信任，**只重测有变化的部分 + 报告里
列出的「未覆盖项」**，每次顺手消掉一条。构建会检查报告是否过期（包里有文件比报告新 → 告警）。

```bash
pnpm run checkdocs            # 看全部包的检测状态；缺的自动补骨架（不覆盖已有）
pnpm run checkdocs -- --list  # 只看状态，不写文件
```

> **骨架不等于结论。** 新生成/未检测的包一律标 `⛔ 未检测` —— 结论只能来自真实的四道门检测。

## 维护纪律

1. **同一份规则只存一份。** 内嵌技能由 `skills.json` 声明、构建时复制，仓库里**没有**副本可改；改规则只改 `packages/<技能名>/`。
2. **图标只在 `avatars/`。** 源包里不放图标，避免两处不一致。
3. **`dist/` 是产物、不入库**（已 gitignore）；`.workbuddy/` 是运行时数据，同样不入库。
4. **提交前跑 `pnpm build`**，确认深度自检通过。**目标状态是「0 项未通过」** —— 2026-09-17 修掉了两条长期误报（专家团成员的 `name` 判定、内嵌副本把 `icon.png` 误判成漂移），18 个包现已全绿。**不再有「可忽略的误报」这一说**：看到红灯就查，不要习惯性划掉。自检脚本自 2026-09-23 起**已搬进本仓库**（`scripts/selfcheck.py` 是权威版本），不再依赖本机技能目录。
5. **上传前由人来做的事**：实名认证 + 人脸核身、点「公开发布」、装回来跑一次验收。
6. **每新增一个技能，必做一次「归置判断」。** 四选一：①保持独立技能 ②并进现有专家 ③新建单专家 ④与别的技能组成专家团。**给出结论和理由后先问再动手**，不要默默建包。
7. **每次收工输出全量清单。** 技能 / 专家 / 专家团逐项列出，**带版本号**；本轮改过版本的标【本地升级】。清单同时体现内嵌技能与成员构成。
8. **改内容就要动版本号。** 版本号跟着包走，不跟着平台走 —— 本地改了但还没传，就要标【本地升级】，否则下次分不清平台上是哪一版。
9. **图标状态不写死在文档里。** 图标变动频繁，任何「已就位 / 待替换」的静态标注都会过期。**唯一权威是 `pnpm run list` 的实时输出**，文档只负责写清「需要哪些文件、什么规格、放哪里」。
10. **技能发布类目看平台判定，不靠猜。** 技能包内没有类目字段，类目是**后台下拉框选的**；被驳回「类目不符」只影响审核，**改类目重提即可，不因此抬版本号**。判定结果回填到「技能发布类目」一节，供下一个技能参考。
    **⚠️ 例外：被判「深度合成」时不能照选（2026-09-28 实证）** —— 该类目**只对企业开发者开放**（个人主体须先企业认证），
    个人主体**选不到** → 这类驳回**改类目解决不了，只能改应用本身**（说明字段沿最近一个过审版本的基线回退 +
    剔除第三方 AI 服务的档位 / 型号 / 额度措辞 + 加显式「无深度合成」声明）。做法见 `docs/平台资产规范.md` 第八节。
11. **文档写了的能力，脚本必须有。** 出过这个坑：SKILL.md 写了「检索默认排除废片」「缺字段由用户补充」，脚本里一条没实现、一条做反了 —— 使用者按文档操作却拿到错误结果。**承诺与实现之间不留缺口，改完必须实测（含反向验证）。**
12. **打包前必须过发布前检测四道门。** 谁打包都一样：AI 代打包也要先做检测，证据就是 `packages/<包名>/<包名>.md` 里**有本轮日期、对应版本等于当前包版本、状态不是「未检测」**。构建会替你把这道关（缺报告 / 未通过 / 版本不符 / 报告比源码旧都会告警，`--strict` 直接失败）。
13. **检测报告只增不改历史。** 每次检测**追加**「检测履历」一行，并更新头部四行；「未覆盖项」**不许空着**（空着 = 没认真写）。下次检测先读报告，只重测有变化的部分与未覆盖项。
14. **报告是开发期文档，不进 zip —— 但进 git。** 构建已自动排除（含被内嵌技能的那一份）；它只在 `packages/` 里活着，别指望从 zip 里看到它。
15. **发布要记账，且必须分清「提交完待审核」和「审核完成」两件事。** 上传之后：该包的 `submitted` 字段填上（**② 提交完待审核**）；**过审之后**再把它落到 `platform` 字段（**③ 审核完成**），并在 `发布清单.md`「六、发布历史」追加一行。**② 只有开发者账号的发布管理页看得到、接口读不到** —— 你不记，清单就会一直显示成「还没提交」，下次分不清该发哪一版。
16. **产物带版本号，同包只留最新一版。** `dist/<包名>-v<版本>.zip`；每次构建自动清理该包的旧版本 zip。zip 第一层仍是包目录名，**外层 zip 文件名不参与平台解析**（带不带版本号都一样）。**注意别把这句读成「改名随便改」** —— 平台解析不了的是外层文件名，而 `zip` 第一层目录名与 `plugin.json` 的 `name` **是**平台侧标识，改包名要过 R7（同改 8 处，见 `docs/平台资产规范.md` 第十二节）。
17. **每次沾发布，都要更新 `发布清单.md`（仓库根）。** 表格别手改（构建会覆盖），要改数据去改 `release.config.json`；但**「六、发布历史」必须每次追加一行**，被打回还要在「五、发布时要注意」写清可执行的下一步。**这是 AI 的固定动作，不是等人的动作**；日期不知道就写「日期未记录」，**不许编**。
18. **推送是人做的事，AI 不碰远程。** 不执行 `git push`，也不去核对本地领先远端几个提交 —— AI 的边界是把提交做在本地。
19. **抬版本号的判据是「有没有走到过『提交成功』」**（2026-09-28 实证，**订正了旧口径**）：**解析失败**（描述超限 / 入口选错 / 结构不符）→ 平台**没占用**该版本号 → 修完**同名重传**即可；**提交成功、进入审核后被驳回** → 版本号**已被平台记录**（显示为「当前最新版本」），同名重传必报 `解析失败：包内版本号「X」必须大于当前最新版本「X」` → **必须抬版本号**，且**内嵌它的包要一起抬**。旧说法「上传即被拒 = 不抬版本号」**只对前者成立**，别外推。
20. **`README.md` 资产总表的四列别手改：状态 / 版本 / zip 体积 / 内嵌技能（版本）已由构建接管**（`syncReadmeTables()`）。它们和 `发布清单.md` 同源，**留一处手工维护就必然漂移**。2026-09-28 实证：只纳管状态列时，`musician` 升到 1.6.0 后本表仍写 `1.3.0 / 35.2 KB`、`cine-team` 行仍写内嵌 musician 1.3.0，**且构建 0 告警**。**判定「还有没有派生列没被纳管」的办法：改一个包的版本 → 跑构建 → 看输出点名了哪些列。** 每列带形状守卫，格子长得不对会**跳过并点名**（不静默）。
