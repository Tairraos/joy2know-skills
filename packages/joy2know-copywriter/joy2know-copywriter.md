## 四、门 3 · 合理性结论

- **规则是否自洽**：✅ 无互相打架。规则 4（合规）与规则 6（腔调）是两道**不同性质**的关：
  前者是硬门禁（命中即改），后者是白名单（只改命中处、其余逐字保留）—— 两者顺序与优先级在文中已区分。
  边界成对写清 —— agent 明写「不做选题」，与上游选题环节的界线用对方的活来解释。
- **推断是否标注为推断**：✅ 相对弱于其它三包（本包以「成品」为主），但两处给了纪律：
  规则 1 的 `【待补：……】` 与规则 8（不写做不到的承接）。
- **错误提示是否可指导下一步**：✅ 降级路径明确（缺关键信息 → `【待补】` 不编填空；找不到合规说法 → 换可验证事实）。
- **边界是否优雅**：✅ §六 覆盖六类边界（不做选题 / 不改定位卖点 / 不承诺效果 / 不代发不代登录 / 待补要报出声 / 不代人转交）。
- **依赖是否守住**：✅ 无网络调用、无凭证；唯一会写文件的是内嵌技能的 `fix.py`，且**默认干跑**、只对指定稿件生效。
- **值来源是否可追溯**：✅ 版本号 1.0.0 三处一致；头像与技能真源均可追。
- **⚠️ 平台字数上限无出处**：五个平台的上限值（22/20/28/22/14）是**经验值**，已就地标注
  「发布前以平台实时规则为准」，但未标出处与取值时间 —— 见弱项 W1。

**一组本包专属的检查替代**：S4（技能名拼错）在本包**改为 `./skills/joy2know-does-not-exist` 才能等价**——
本轮用的是 topic-planner 上的同名样本，两个包的内嵌机制完全相同（同一段代码路径），故未重复造。

**一句话回答：本包的核心结构如果坏掉，是哪一步会亮红灯？**

→ 平台解析层（配置字段 / 内嵌技能名 / 描述字数 / 头像路径）坏了 → `selfcheck.py` 亮红灯。
→ 交付形态层（zip 第一层、内嵌副本漂移、头像注入）坏了 → 解压后的交付形态自检亮红灯（13 项）。
→ 腔调层（规则表被改坏）坏了 → 内嵌技能的 `selftest.py` 亮红灯。
→ **有一类不会亮红灯**：成品文案的**实际质量**（标题够不够吸引、改写是否真按平台脾气、门禁在真实对话里是否真被跑）——
  自动校验只能确认「规则写了」，读不出「规则被执行了」。这是本包最大的未覆盖面（见第六节 1）。

## 六、未覆盖项 / 已知缺陷 / 待办

**未覆盖项**：

1. **成品文案实际质量未评估**，且**「门禁是否真被跑」这一行为未验证** —— 本轮在构建产物里跑通了 `selftest.py`
   证明脚本可用，但**无法证明 agent 在真实对话里调用过它**。这是行为层验证，需真实写一轮才能观察 —— **最大未覆盖面**。
2. **平台标题字数上限无出处**（见弱项 W1）。
3. **平台侧真实上传 / 解析 / 审核未实测**。
4. **`categoryId` 取 `05-MarketingGrowth` 是推断值**：平台是否认可**未经实证**。
5. **内嵌 `humanize` 与本包职责的边界未做对抗测试**：理论上「写文案」与「去 AI 味」是两步，
   但真实写作中两者会交织（一边写一边改）。是否会出现「反复过门禁把文案改坏」，未测。

**已知弱项**：

- **W1 · 平台字数上限无出处**：22/20/28/22/14 是经验值，已标「以平台实时规则为准」，未标出处与取值时间。
- **W2 · 文案长度/结构无量化判据**：除标题字数外，正文长度与结构只给了定性指引（「段落长度」「钩子形态」）。
  不设硬阈值是刻意的（形态差异过大），但代价是缺可勾选的判据。

**待办**：

- 出真头像 → 覆盖同名文件 → 重跑 `node scripts/build.mjs joy2know-copywriter`。
- 真写一轮多平台文案，观察门禁是否真被调用（未覆盖项 1）。
- 首次提交后回填 `release.config.json` 的 `submitted`。
