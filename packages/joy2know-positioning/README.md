# 产品定位与卖点专家（joy2know-positioning）

> 把参数翻译成用户能感知的好处，再决定先打哪个平台。

## 他解决什么问题

好产品卖不动，最常见的原因不是产品不行，是**讲的东西用户感知不到**：

- 满篇「80 项检测能力」「技术领先」，用户看完不知道自己会得到什么；
- 一句话定位写得像口号，问「和谁不一样」答不上来；
- 只讲好处，不处理「用户觉得没必要」这一层 —— 而推广真正要打的往往就是这一层；
- 渠道选择跟着「哪个平台火」走，而不是跟着「人在哪、我们做不做得出来」走。

## 三条底线

1. **卖点是好处，不是参数。** 每条都走「特性 → 这意味着什么 → 所以用户得到什么」，只把最后一步写进卖点。
2. **定位必须过「和谁不一样」这一问。** 三个空（谁 / 什么价值 / 和谁不一样）填不出第三个，就如实说「这个品类目前没有可讲的差异化」，并给可选动作 —— 不编一个。
3. **不做减法等于没排序。** 渠道矩阵必须写出「先放弃哪几个、为什么」，理由落到「人群不对 / 形态不匹配 / 我们做不出来」三者之一。

## 包内容

```
joy2know-positioning/
├── .codebuddy-plugin/plugin.json         核心配置
├── agents/joy2know-positioning.md        角色定义（系统提示词）
├── avatars/expert.png                    头像 512×512（由构建注入）
├── skills.json                           内嵌技能清单（本包不内嵌技能）
└── README.md
```

**本包不内嵌技能** —— 它的方法论是「翻译三步法 + 四问定位 + 渠道四项打分」，属于角色定义的一部分，没有可复用的独立计算逻辑。

> **形态说明**：上面的目录树是**构建后所得包的形态**。仓库里的**源包**只有
> `.codebuddy-plugin/plugin.json`、`agents/joy2know-positioning.md`、`skills.json` 与 `README.md` ——
> `avatars/` 由构建从仓库根 `avatars/joy2know-positioning.png` 注入。

## 怎么用

| 你说 | 他做 |
|---|---|
| 帮我定一句话定位 | 特性 → 好处 → 差异化 → 定位卡 |
| 我的卖点该提炼成什么 | 三条用户语言的卖点 + 落地场景 + 砍掉哪些 |
| 用户觉得没必要，我该怎么讲 | 反对意见清单 + 一句可接受的回应 |
| 先打哪个平台 | 四项打分的渠道矩阵 + 先放弃哪几个（含理由） |
| 我没什么同类信息 | 先做轻量品类判断，差异化标 `【假设-需验证】`，并列 2–3 个待确认问题 |
