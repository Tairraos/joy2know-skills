# 投放效果复盘专家（joy2know-reviewer）

> 「数据不好」不是结论，是问题的开头。

## 他解决什么问题

内容发出去之后，最常见的一幕是：数据摆在那儿，看不出问题，也想不出下一步。

- 有曝光没人点、有人点没人读完、有人读完没人动 —— 三种问题，解法完全不同；
- 只有两条数据就下结论「A 类选题更好」，然后照着错的方向做一个月；
- 归因归到「平台算法变了」，于是什么也没改；
- 数据攒在后台，没人整理成一页能给领导看的东西。

把这一环补上：**先对齐，再分层，先证伪，最后落到「谁改什么」。**

## 三条底线

1. **先对齐再分析。** 拿 A 条的数据解释 B 条的表现，是复盘里最常见的坑，结论必然错。对不上的数据标出来，不用。
2. **归因必须落到漏斗某一层。** 「整体效果不好，建议优化一下」等于没说。五层是：曝光 / 点击 / 完读 / 行动 / 承接。
3. **先证伪自己，样本不够就不下结论。** 每条结论都要写至少一个能推翻它的解释；内容少于 5 条时只给实验设计，不给规律。

## 包内容

```
joy2know-reviewer/
├── .codebuddy-plugin/plugin.json       核心配置
├── agents/joy2know-reviewer.md         角色定义（系统提示词）
├── avatars/expert.png                  头像 512×512（由构建注入）
├── skills/joy2know-dashboard/          内置技能（一页看板，由构建注入）
│   ├── SKILL.md
│   └── references/chart-choice.md      图表选型细则
└── README.md
```

**看板的做法在 `skills/joy2know-dashboard/`，与独立上架的技能包同源。** 角色定义只规定「什么时候出看板、看板里必须有什么」。

> **形态说明**：上面的目录树是**构建后所得包的形态**。仓库里的**源包**只有
> `.codebuddy-plugin/plugin.json`、`agents/joy2know-reviewer.md`、`skills.json` 与 `README.md` ——
> `avatars/` 由构建从仓库根 `avatars/joy2know-reviewer.png` 注入；`skills/` 由构建按 `skills.json` 声明的名单复制**唯一真源**。

## 怎么用

| 你说 | 他做 |
|---|---|
| 这批内容数据在这，问题在哪 | 对齐表 → 分层归因 → 下一轮建议（每条标归谁） |
| 有曝光没人动，为什么 | 按漏斗逐层排查，指出是标题、时间还是承接 |
| 我只有播放量 | 明说「不足以定位到层」，列出还需补哪些字段 |
| 就两条数据 | 只给实验设计（测什么、怎么分组），不下规律结论 |
| 做个能发给领导的看板 | 一页单文件 HTML，图里每个数字能指回对齐表 |
