# 晓得 · harness 工程化规则

> 把「一个项目」变成「**智能体优先（agent-first）的 harness 工程化形态**」：**人类掌舵，智能体执行。**
> 两条路线共用同一套信条，**互斥、不许混用** —— 空仓库走新建，已有业务代码走改造。
>
> `@references/` 里是两份**自包含施工图全文**（母本原文，一字未改）。
> **不读对应的那一份就动手，一定会跑偏。**

## 一、先分清（不做这一步后面全错）

| 概念 | 判定标准 | 处理方式 |
|---|---|---|
| **起点** | 用户手上有没有能跑的业务代码？ | 有 → 改造路线；没有 → 新建路线 |
| **harness 工程化** | 把工程重心从「写代码」移到「设计环境、明确意图、构建反馈回路」 | 不是写一堆规范文档，是**把约束变成可机械执行的东西** |
| **施工图** | `references/` 那两份规则文档本身 | 施工期全文常驻目标仓库；**竣工必须拆解归档**，不许当僵尸文件 |
| **母本 vs 副本** | 母本 = 本技能 `@references/`；副本 = 复制进目标仓库的那一份 | 两处都要改时，**先改母本再回流副本** |
| **不变量（invariant）** | 必须始终成立、可被机械检查的约束 | 能写成 linter / 结构测试的，文档里就不要重复写 |

**最容易犯的错：把两份文档当参考资料读一遍就开工。** 它们是施工图 —— 要逐节执行、逐项勾选，
末尾的验收清单没勾完不算做完。

**第二容易犯的错：把新建那份的规则套到存量项目上。** 新建的框架判定是「从需求确认」，
改造的框架判定是「从文件扫描」—— 同一件事，两份文档的答案是相反的，混用必然错。

## 二、判定与路由

| 情形 | 判定信号 | 走哪条 | 用哪份 references | 第一动作 |
|---|---|---|---|---|
| **A. 从零新建** | 空仓库 / 只有需求没有代码 | 新建路线 | `@references/new-project-harness-rules.md` | **先索取需求**，复述确认，再定技术栈（该文档 §3.2） |
| **B. 存量改造** | 有业务代码，哪怕只有一个源文件 | 改造路线 | `@references/turn-project-to-harness-rules.md` | 只做**阶段 1**：扫描 + 出计划，**一行业务代码都不许改** |
| **C. 只要规则不施工** | 「把规范给我，我自己贴到项目里」 | 只交付施工图 | 对应那一份 | 复制到目标仓库 `docs/HARNESS-RULES.md`，再把开场提示词一并交给用户 |
| **D. 只补某一项** | 「只加 CI」「只补 AGENTS.md」「只加 linter」 | 降级：进对应章节 | 对应那一份的相关节 | **先说明「局部落地会缺护栏」**，再按该节执行；不许自称已完成整体 harness 化 |
| **E. 只想评估** | 「我这项目离 harness 化还差多远」 | 只出诊断 | 改造那份的阶段 1 | 扫描 → 给差距清单与分批建议，**不落地改动** |

**判定歧义时问，不要猜。** 一句「你手上有能跑的业务代码吗」就能定下来。
用户答「有个空目录」→ A；答「有个能跑的项目」→ B；答不上来 → 让用户把目录内容说一遍再判。

## 三、工作流

```
① 判定起点（§二 的五个情形）
        │
        ├─ 不确定 → 问一句，别猜
        ↓
② 加载对应的 references 全文
        ↓
③ 新建：索取需求 → 复述确认 → 定技术栈 → Day 0 十项 → 阶段 A–G 逐阶段勾选
   改造：阶段 1 扫描 → 计划交人确认 → 2 文档 → 3 门禁 → 4 重构 → 5 测试 → 收官拆解
        ↓
④ 每个决策点交互确认，结论当场落盘进仓库
        ↓
⑤ 交付前逐条自检（§八）
```

**两条路线的「第一动作」完全不同，这是路线判定的意义所在：**

- **新建路线**的第一动作是**索取需求**。空仓库里没有任何信息能告诉任何人「要做什么」——
  需求不明就开工，等于替用户做产品决策（该文档 §0 反模式第一条）。
- **改造路线的第一动作是扫描**。已经有代码了，需求藏在代码里，但**必须先把现状变成一份
  可评审的计划**，计划没被确认前不许动业务代码（该文档 §0 契约 C1）。

## 四、核心规则（两条路线共用，细则见对应文档章节）

这七条之所以单独列在这里，是因为它们**跨两份文档都成立**，而且是路线判定之后最先要守住的：

| # | 规则 | 细则在哪 |
|---|---|---|
| H1 | **不许假设技术栈 / 目标平台 / 发布方式。** 这三样都是「不可从代码推断的用户决策」，不明就问 | 新建 §3.2–§3.4；改造 §3.2–§3.3 |
| H2 | **交互确认必须落盘。** 只在对话里确认过、仓库里没有记录的决策，等于没做 | 新建 §2.2；改造 §0 契约 C5 / §3.3 |
| H3 | **`AGENTS.md` 是地图不是百科。** 目标约 100 行，只做目录；超 200 行就是反模式 | 新建 §2.3；改造 §2.2 |
| H4 | **先护栏后动手。** 没有门禁保护的代码，先补保护再重构 | 改造 §0 契约 C3 / §9 红线 R3 |
| H5 | **行为守恒。** 重构不改业务行为；行为变更必须显式登记并单独提交 | 改造 §0 契约 C4 / §9 红线 R1–R2 |
| H6 | **一切进仓库。** 智能体运行时看不到的东西，对它来说就不存在 | 新建 §2.2；改造 §1.2 信条 B3 |
| H7 | **施工图竣工必须拆解。** 一次性流程归档、长效契约迁移进常驻文档；**拆解自检没过就不许删** | 新建 §16；改造 §14 |

**H7 是最容易被跳过、后果最隐蔽的一条。** 一份近千行的规则文档永久常驻在 `docs/` 里，
会同时违反它自己的两条主张（「地图不是百科」「入口要小」），并必然与项目现状漂移 ——
**僵尸文件比没有文件更糟：它会让下一个智能体照着错的规则干活。**

## 五、输出格式

**新建路线**（按该文档 §13 逐阶段验收）交付：

1. 需求澄清结论 + **技术栈结论五项**（目标平台形态 / 语言 / 框架 / 包管理器 / 构建方式）
2. Day 0 十项（该文档 §1.2）—— `.gitignore`、格式化、包管理器、目录骨架、`AGENTS.md`、
   `ARCHITECTURE.md`、`docs/` 结构、首批 linter 与结构测试、CI 骨架、框架与 CI 决策
3. 阶段 A–G 的勾选结果；能落成机械检查的，就落成机械检查

**改造路线**（按该文档 §5 与 §11）交付：

1. **阶段 1 只交两件东西**：`docs/exec-plans/active/harness-migration.md`（改造计划）+
   `docs/exec-plans/tech-debt-tracker.md`（问题清单，字段定义见该文档附录 B）
2. 阶段 2–5 的产出（`AGENTS.md` / `ARCHITECTURE.md` / 文档树 / 门禁与 CI / 重构提交 / 测试与覆盖率）
3. 收官拆解产物：`docs/exec-plans/completed/harness-<YYYY-MM-DD>.md`

**改造计划里的每一条问题都必须带**：ID、位置（文件:行）、类别、严重度、**证据**、修复建议、
**是否改变业务行为**。没有证据条目的计划视为未完成（该文档阶段 1 禁止事项）。

**动作主体是目标仓库**，不是你自己的输出目录 —— 写文件要写进用户给的那个项目里。

## 六、防幻觉

- **不许编日期。** 不知道就写「日期未记录」。
- **不许编技术栈、平台、发布方式。** 这三样只能来自用户回答；用户没答就停下来问（规则 H1）。
- **不许把「扫描了」说成「审计过了」。** 每条问题都要能指到具体文件与行号，指不到就登记为「待核实」。
- **不许把「文档写了」当成「已验证」。** 门禁必须**注入一个该被拦的缺陷实测一次**才算数
  （改造文档阶段 3 验收标准明确要求「故意引入越层依赖，门禁必须失败」）。
- **不许替用户拍板要不要 CI、build 哪些平台、Release 走不走 draft。** 猜错等于白做。
- **用户选了 draft，就不许再加自动转正兜底。** 那是直接违背用户意图。
- **不许因为「这段不适用」就顺手删掉存量配置。** 存量项目的现有 `release.yml` 先审计、
  把差异摆给用户看，再决定改造还是重建。

## 八、完成判据

**新建路线**：该文档 §13 的阶段 A–G 全部勾完，且 §16.6 的收官自检通过
（把施工图从仓库移除后，仅凭 `AGENTS.md` + `core-beliefs.md` + `ARCHITECTURE.md`
仍能遵守全部硬约束）。

**改造路线**：该文档 §11.1 的十条 DoD 同时满足，其中第 10 条同样是收官拆解自检通过。

**两条路线共同的交付前逐条自检：**

- [ ] 起点判定有明确依据（说得出为什么是新建而不是改造）
- [ ] 技术栈五项的每一条都能回溯到「用户的需求」或「用户的确认」，**没有一条是自行假设的**
- [ ] 所有交互确认都能在仓库里找到落盘记录（不是只在对话里说过）
- [ ] 若走了改造路线：阶段 1 结束时 `git diff --stat` 证明**未改任何业务代码**
- [ ] 若涉及 CI：三问被**逐条**问过、答案落盘、matrix 严格按用户勾选裁剪、**没有擅自多加平台**
- [ ] 若用户选了 draft：release 流程里**不存在**自动转正兜底
- [ ] 门禁不是纸面的 —— **注入过一个该被拦的缺陷，实测被拦下**
- [ ] `AGENTS.md` 行数达标，且通篇是「指向」而非「说明」
- [ ] 施工图竣工时已按拆解映射表归档，且「移除后仍能遵守硬约束」的自检通过
- [ ] 未覆盖项 / 待人工决策项已单列成表，不是被悄悄跳过

**一句话判据**：如果这份交付里的某条约束坏掉了，**是哪一步会亮红灯**？答不上来的约束，
就是没人看着的约束 —— 把它变成机械检查，或者明说它靠人守。

## 九、降级与跨轮次

| 情形 | 降级怎么做 |
|---|---|
| **用户什么都说不出**（没有需求、没有代码、说不清要做什么） | 不猜。先给一个「立项问题清单」（这个项目给谁用、解决什么、跑在哪里），让用户挑着答。**一条都答不出就停在这里** —— 这是新建路线的硬前置 |
| **用户只要文档** | 走 §二 情形 C，只交付施工图 + 开场提示词，并**明确告知**：规则文档是施工图，竣工要拆解 |
| **项目太大，一次做不完** | 改造路线本来就按业务域分批；把剩余批次写进计划的「待人工决策清单」，**每轮只推一个批次** |
| **用户中途改主意**（走了一半要换路线） | **停下来重新判定起点**。已完成的阶段产物能留就留并说明，不能留的明说作废；**不许把两份文档混着用** |
| **目标项目里已有同类规范** | 先做**冲突盘点**：哪些是重叠、哪些是互斥。互斥项交用户裁决，**不许静默覆盖** |
| **取不到 git / 命令行** | 明说哪些验收项（如 `git diff --stat` 自证、门禁实测）因此无法完成，降级为人工核对清单，**不许假装做过** |

**跨轮次**：这套东西天然是多轮次的（改造五阶段、新建七阶段）。每轮开工先读目标仓库里的
`docs/HARNESS-RULES.md` 与 `docs/exec-plans/active/` 下的计划，**从进度日志接着走**，
不要从头再来一遍；每轮收工更新计划的进度与决策日志。
