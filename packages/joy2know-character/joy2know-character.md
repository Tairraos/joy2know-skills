## 四、门 3 · 合理性结论

- **规则是否自洽**：⚠️ **发现一处不一致**。§一 表格「造型」行写「算**另一把锁**，另建一张卡」，
  而规则 4 写「新建一张角色卡**或卡的独立 `variant` 块**」，`spec` §四 给的正是单卡内 `variant` 块的示例。
  §一 未同步规则 4 的 `variant` 方案 → 照 §一 理解会以为「必须新建一张卡」。两条规则目标相同（另起一把锁），
  差异只在落盘形态，**属表述不一致而非逻辑冲突**。详见第六节缺陷 1。
  除此以外 5 条规则互不打架：规则 1（逐字进提示词）与规则 3（最小短语、禁句号/动作/状态）取向一致；
  规则 2（状态不上锁）与 §五 骨架的 `state_excluded` 一致。
- **推断是否标注为推断**：✅ §六.3 要求把「用户给定 / 参考图可见（注明哪张）/ 我推断（标 `[推断]`）」分清；
  §六.2 要求「锁不住就说锁不住」、不许硬编。规范层自洽且措辞可执行。
- **错误提示是否可指导下一步**：不适用（纯文档技能，无脚本、无报错路径）。
- **边界是否优雅**：✅ §九 覆盖四种边界（信息不全 / 参考图缺失 / 跨轮次续用 / 用户嫌卡太长），
  §二 另有「只想先出一张图试试 → 走最小卡」的降级。文档类技能不存在「崩」，边界处理看「有没有给路径」——给了。
- **零依赖是否守住**：✅ 结构性成立（无 `scripts/`、无 import、无网络调用）。
- **值来源是否可追溯**：✅ spec §一 每个字段标注 必填 / 建议 / 可选；§六.3 要求标来源；
  未提供时要求标「未提供，暂不锁」，**明确禁止凭空补值**（§六.1 禁止凭「一般主角都长这样」编发色瞳色）。
