把**已经写好**的稿子或数据，变成**能直接交出去**的版本。四位编辑各管一棒，主理人「闻山」先体检再分派。

## 与流水线式团队的区别：先诊断，不是四棒全上

四棒全开的结果是一份谁都不认得的稿子 —— 结构被重排、措辞被换掉、观点被压扁。所以主理人的第一件事是**体检**：从材料里找证据，判断它到底卡在哪一棒，只调对应的人。

```
Phase 0  体检（闻山，引原文作证据）
            ├── 「不知道重点在哪」 → 林知
            ├── 「太长，讲不完」   → 简宁
            ├── 「是表格，没人翻得动」 → 方寸
            └── 「读着像机器写的」 → 苏白
Phase 1  条理（林知）
Phase 2  提炼（简宁，按需）
Phase 3  可视化（方寸，按需）
Phase 4  语气（苏白，必做，且永远最后）
Phase 5  汇编为《定稿》（闻山）
```

## 顺序铁律：语言编辑必须是最后一棒

```
条理（重排结构）→ 提炼（压缩容量）→ 可视化（换形态）→ 语气（改腔调）
```

三条理由：

1. 语言编辑的规矩是「只改命中的地方，其余逐字保留」—— 先过语气再动结构，刚改好的句子会被打散，这一遍白做。
2. **结构编辑本身会引入腔调**（重排时很容易写出「先说结论：」这类提示语），顺序反了，机器腔调会从结构层渗回来。
3. 语气是唯一一道「可能改坏内容」的工序，自带四道门禁，必须作用在最终定稿上才算数。

## 内置技能

- **joy2know-clarify（晓得·讲明白）**：结论先行、分层展开、该配图时主动配图
- **joy2know-humanize（晓得·凡人腔调）**：规则表驱动去机器腔调，带脚本自检与改写门禁
- **joy2know-deck（晓得·讲得清）**：长报告提炼成能讲的篇幅，每页附口播稿
- **joy2know-dashboard（晓得·一页看懂）**：表格 → 单文件交互式 HTML 看板

## 适用与不适用

- **适用**：稿子写完了但交不出去（太乱 / 太长 / 太像 AI 写的）；手里的表格没人看得懂；交稿前想过一遍
- **不适用**：
  - **从零创作** —— 没有初稿时先弄一份糙稿出来，糙稿可以打磨，空稿不行
  - **事实核查** —— 只处理表达与形态，材料本身说错了什么不负责发现
  - **改变观点与判断强度** —— 「可能有效」不会变成「有效」
  - **承诺「AI 检测率降到多少」** —— 任何百分比承诺都是假的

## 目录结构

```
joy2know-polish-team/
├── .codebuddy-plugin/plugin.json   # 配置（expertType: team）
├── settings.json                   # 主理人声明（平台校验器查这个名）
├── setting.json                    # 内容同上，沿用官方模板名，兼容保留
├── agents/                         # 1 主理人 + 4 成员
├── avatars/                        # 团队头像 + 5 角色头像（由构建注入）
├── skills/                         # 内置 4 技能（由构建注入）
└── README.md
```

> **形态说明**：上面的目录树是**构建后所得包的形态**。仓库里的**源包**只有
> `.codebuddy-plugin/plugin.json`、`agents/`、`skills.json`、`settings.json`、`setting.json` 与 `README.md` ——
> `avatars/` 由构建从仓库根 `avatars/joy2know-polish-team/`（团队图标）+ `avatars/<成员名>.png`（成员图标）注入；
> `skills/` 由构建按 `skills.json` 声明的 4 个技能名，从 `packages/<技能名>/` 复制**唯一真源**
> （本包内不存副本，避免同一技能两份、改一处漏一处）。
