# 技能包组装

**两件事：该做成什么形态（归置），以及怎么写才对（写作）。**
字段填什么、打包检测、驳回处置、状态读取都不在这里。

---

## 一、先做归置判断：这个技能该不该做成专家

每新增一个技能，**先过这一关，给出结论和理由再动手**，不要默默建包。

### 四选一

| 选项 | 什么时候选 | 成本 |
|---|---|---|
| ① 保持独立技能 | 不从属于任何流水线，单独用最顺手 | 0 |
| ② 并进现有专家 | 与某个专家同线，扩一句 `profession` 即可 | 低（要重传该专家） |
| ③ 新建单专家 | 自带完整人格与判断空间，**且能独立开场** | 1 包 + 1 图 |
| ④ 与别的技能组专家团 | 天然是某条流水线的一环（有上游输入、有下游交付） | 1 包 + settings.json & setting.json + N 个 agent + N+1 张图 |

### 两条抓手（能挡掉大部分「其实不该做专家」的技能）

**抓手一：输入从哪来。**
技能只能吃「别人产出的东西」＝ **加工环节**，不适合做单专家 ——
用户点进去还得先粘一篇稿子，开箱体验很糟。**能从一句需求从零产出的，才适合单专家。**

**抓手二：规矩松紧。**
「只改命中处、其余逐字保留」这类硬纪律，与人设鼓励的即兴发挥**相冲**。
判定：**规矩钉得越死，越该做成团队里的一棒，而不是一个人格。**

### 单飞判据（三条须同时成立）

| 判据 | 问什么 |
|---|---|
| 输入自足 | 用户手上直接就有它要的东西，不必等别的一棒产出 |
| 有独立检索需求 | 用户会**单独搜**这个能力，而不是搜「整套流程」 |
| 交付物独立可用 | 产出脱离团队上下文仍是一件完整的东西 |

三条不齐的，多半是**接棒型角色**（调度者、排期官）—— 留在团内更合适。

### 专家团编排的四条经验

1. **先问「是不是固定流水线」。** 是 → 按阶段顺序编排；不是 → 主理人必须先**诊断**再分派。
   诊断要有依据，引原文作证。
2. **工序顺序要能说出理由，不能只是"看着顺"。** 典型：把「去腔调」这类**减量、易改坏内容**的
   工序排在最后。理由至少三条，写进 agent 文件。
3. **相邻两棒的界线要写成硬规矩**，否则一定糊。用**对方的活儿**来解释边界。
4. **主理人的「严禁行为」必须写成可观测判定。** 光写「不许代写成员内容」没用；
   要写成「回复里出现『甲认为……乙建议……』这种一口气写多角色的内容即为违规」。

### 别人的 agent skill 要不要「收进来」？先过三关

| 关 | 判定 | 不过怎么办 |
|---|---|---|
| 许可关 | 仓库根有无 `LICENSE`。**没有 = 默认保留所有权利** | 直接排除。**上游自身的授权也要看** |
| 依赖关 | 引擎体积几十 MB~数百 MB，**装不进 3 MB 技能包** | 只写「调用本地已装工具 + 安装指引 + 降级」 |
| 输入关 | 只能吃别人产出的东西 → 加工环节 | 做技能，**不做专家、不组团** |

⚠️ **值得建团的线要 5~7 棒；只有 2~3 棒的做技能就够，做团是过度设计。**

⚠️ **「合并进现有包」与「内嵌进现有包」是两回事。** 内容合进别人的技能里会污染它写死的边界；
而内嵌机制让新技能**保持独立可售、同时被专家内嵌**，两边用户都够得着，且不产生副本。

## 二、`description` 是产品本身

技能靠 `description` 匹配触发，**`name` 不参与触发** ——
改 `name` 对触发零影响，改 `description` 才是改产品。

### 四条写法

1. **触发词要写全**（含同义口语），并明确写**不适用于**什么 —— 后者能防误触发。
2. **长度要压在系列区间内**：经验区间 **240–390 字**。新手容易写到 600+ 字
   （把「适用范围 + 不适用 + 触发词 + 边界」全塞进去），**超标近一倍会稀释触发权重**。
3. **反直觉的取舍：`display_name` 越泛，`description` 越难压。** 名字宽而能力窄时，
   边界全靠 description 承担，字数必然膨胀 —— **遇到这种落差，先改窄名字**，
   比在 description 里堆边界划算。
4. **信息块不删，句子要并。** 修超限的优先做法是**并句删冗词**，不是砍掉信息块。

### 触发不到的三种自查

| 症状 | 原因 | 修法 |
|---|---|---|
| 用户口语说「帮我做个 skill」但没触发 | 触发词只写了书面词 | 补口语同义词 |
| 该触发时被别的技能抢走 | 边界没写「不适用于」 | 补排除项 |
| 名字太泛、什么都想接 | `display_name` 宽而能力窄 | 改窄名字 |

## 三、系列一致性七条硬规则

改包必过。**同一骨架会批量复现同一缺陷。**

| # | 规则 | 违反的后果 |
|---|---|---|
| R1 | **降级必须留痕** | 静默失败、静默丢弃 |
| R2 | **实现里有的能力，文档必须写** | 「文档写了、实现没做」与反向漏写 |
| R3 | **同一规则只允许一种表述** | 口径漂移，改一处漏一处 |
| R4 | **references 的「必做类」章节必须被正文点名** | 写了但模型不读，等于没写 |
| R5 | **派生数值必须自洽可推** | 两处数字迟早不一致 |
| R6 | **同类缺陷必须全系列扫一遍** | 只修观察到的那一个 = 没修 |
| R7 | **已上线的包 `name` 冻结** | `name` 是平台侧不可变主键，改名被驳回 |
| R8 | **升一个技能，必查「谁内嵌了它」** | 内嵌方版本不匹配且 **0 告警** |

### R8 的完整做法

```bash
grep -rl "<技能名>" packages/*/skills.json packages/*/.codebuddy-plugin/plugin.json
```

构建对「内嵌技能」列只做**实时读取、不拦版本不匹配** —— 会出现「清单嵌着新版、旧 zip 里是旧版」
且 **0 告警**。

**两层过期**：① 包版本号没抬；② **成员 `agents/*.md` 正文复述了被引用技能的规则**
（自检不看正文 → 团队会照旧指令人做错事，自检全绿）。

收尾必查：

```bash
unzip -p dist/<包>-v<版本>.zip <包>/skills/<技能>/SKILL.md | grep -m1 '^version:'
```

并 `diff` 内嵌 reference / 脚本与源包。

### 未上线的包要改名：同改 8 处

目录 · `plugin.json` 四处 · 角色文件名与 frontmatter · 检测报告文件名 · 自身图标 · 台账与配置键。

**批量替换文本之后，必做三步验收**（实际改动 ↔ 计划清单，两边集合必须相等）。

## 四、本技能的边界

- **只管「做什么形态」与「怎么写」**。字段取值 → 「资产字段规范」；
  检测与报告 → 「资产包门禁」；驳回处置 → 「发布与驳回」；状态读取 → 「资产状态追踪」。
- **归置结论必须带理由**，不允许只给选项不给判断。
