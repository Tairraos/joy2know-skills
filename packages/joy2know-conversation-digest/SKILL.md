# 晓得 · 对话归纳

把「一个空间里的 N 个对话」还原成一份能交付、能复盘、能接力的**学习流水文档**。

本技能固化的是 **WorkBuddy 会话记录的真实存储结构与提取脚本**（2026-09-14 实测核验）。核心价值只有一条：

> **结构化数据和对话里的叙述经常对不上。产物的真实来源，只能从记录里的写文件调用读出来，不能靠回答文字里提没提名。**

---

## 一、先分清：这是「归纳」还是「别的」

「对话归纳」听着很宽，但本技能能读的只有一处：**本机 WorkBuddy 的会话记录**。动手前必须先把它收敛成一句可执行的判断，否则会去干不属于本技能的活。

| 用户真正想要的 | 归谁 |
|---|---|
| 把我某段时间在 WorkBuddy 里的对话整理成复盘 / 流水 / 总结 | **本技能** |
| 把一个空间（工作区）下的多个对话一起归拢成一份阶段文档 | **本技能** |
| 把某次对话的产物文件归档，并指明名字与位置 | **本技能** |
| 归纳我微信群里聊了什么 / 这份会议纪要讲了什么 | 不归本技能（**没有 WorkBuddy 记录可读**） |
| 把 ChatGPT 导出的 conversations.json 整理成笔记 | 不归本技能（格式不兼容，别硬套） |
| 把散落的文件按名字、大小、时间整理 | 不归本技能（那是文件管理器） |
| 单纯回答一个问题、不需要交付文档 | 不归本技能（直接答就行） |

---

## 二、判定路由：先确认「这是 WorkBuddy 的对话」

**这是本技能的硬门禁，优先级高于后面所有章节。**

### 2.1 放行条件（三条同时成立）

1. 对话发生在 **WorkBuddy 应用内**；
2. 本机存在对应的会话记录：`~/.workbuddy/projects/<某个目录>/*.jsonl`；
3. 用户能指认目标范围（某空间 / 某几个对话 / 某段时间）。

满足即进入第三节工作流。**不要问用户要对话原文——记录就在本机，自己去读。**

### 2.2 拦截条件（命中任一条 → 只解释，不动手）

| 用户递来的东西 | 处理 |
|---|---|
| ChatGPT / Claude / Gemini / 豆包等导出文件（`conversations.json`、`.md` 导出、分享链接） | 拦截 |
| 微信 / QQ / 飞书 / 钉钉 / 企业微信聊天记录（含转发出的 zip 包） | 拦截 |
| 会议录音转写、智能纪要、访谈记录 | 拦截 |
| 邮件往来、工单、评论区截图 | 拦截 |
| 一段直接粘贴进对话的「对话文本」、PDF / Word / 图片里的聊天内容 | 拦截 |
| 用户只说「帮我归纳一下我的对话」但没指出是哪个空间 | **先反问**，不要猜 |

### 2.3 拦截时怎么说（照这个口径，别自己发挥）

> 这个技能只能归纳 **WorkBuddy 里的对话**——它读的是本机 WorkBuddy 的会话记录。
> 你给的这份是「某某平台」的对话，WorkBuddy 里没有它的记录，所以我归纳不了。
> 如果这段内容你本身已经在 WorkBuddy 里聊过，告诉我大概时间或空间名，我去找；
> 如果是别处的对话，可以直接把内容贴给我，我按普通文本帮你整理——但那不走本技能。

**三条纪律：**

- **不要为了「完成度」而降低门槛。** 拿别的平台的对话硬套本技能的结构，会产出看起来像归纳、实际全靠脑补的文档。
- **不要假装读过。** 没有 jsonl 就是没有。
- **被拦截不等于不帮忙。** 降级为「普通文本整理」是允许的，但要说清这不是本技能的产出。

## 三、工作流

### Step 1 · 定位空间与对话

先看清本机有哪些空间、各自包含哪些对话：

```bash
python3 scripts/extract_flow.py --list
```

输出：每个空间的**显示名 → 真实路径 → 其中的对话 ID / 时间范围 / 提问条数**。

判定用户说的是哪一个。若空间名对不上，用关键词在输出里搜。

### Step 2 · 跑提取

推荐按**空间路径**提取（脚本会自动映射到对应的 project 目录）：

```bash
python3 scripts/extract_flow.py --workspace "<空间绝对路径>" --out /tmp/flow/
```

也可以直接给 project 目录，或只提取其中几个对话：

```bash
python3 scripts/extract_flow.py --project ~/.workbuddy/projects/<目录名> --out /tmp/flow/
python3 scripts/extract_flow.py --project ~/.workbuddy/projects/<目录名> --sessions a1b2c3,d4e5f6
```

产出四类文件：

| 文件 | 内容 | 怎么用 |
|---|---|---|
| `manifest.json` | 结构化总数据（空间、对话、时间、计数、产物清单） | 写文档时直接引用，避免手抄错 |
| `users.md` | 每个对话的全部提问（已剥壳、已去重） | 建立「问了什么」的骨架 |
| `answers.md` | 每个对话的回答 block（截断预览） | 判断每轮的核心结论 |
| `products.txt` | 每个对话的写文件清单（保序 + 次数 + 操作类型） | 核对产物归属 |

**阅读顺序固定：users → answers → products。** 先骨架、再内容、最后核对归属。

### Step 3 · 与目录实际内容交叉核对

```bash
ls -la "<空间路径>"; find "<空间路径>" -type f | wc -l
```

把 `products.txt` 跟目录实际文件对齐。**对不上的必须单独判定归属**，不能含糊带过：

- **目录里有、记录里没有** → 可能来自其他对话、或用户手工放进来的。**不纳入归档**，并在文档里写明原因。
- **记录里有、目录里没有** → 已被覆盖或删除，如实标注。

### Step 4 · 归档产物（用户要求归档时）

复制，**不是移动**：产物文件**原文一字不改**地复制到目标位置，且与总结文档**分开放**（总结只列名字与位置，不把产物内容嵌进总结）。

复制后必须校验，校验不通过不算完成：

```bash
md5 -q "<源>" ; md5 -q "<目标>"      # 单文件逐份比对
diff -r "<源目录>" "<目标目录>"        # 目录递归比对
```

### Step 5 · 产出交付文档

默认骨架见第五节。**写完必须做两件事**：数字交叉核对、HTML 标签平衡校验。

## 四、核心规则四件套

### 4.1 存储结构（别猜，照着查）

| 要找什么 | 去哪里 |
|---|---|
| **空间显示名 → 真实路径** | `~/.workbuddy/workspace-display-names.json`（取 `workspaces.<path>.displayName`） |
| **空间包含哪些会话** | **脚本读的是 jsonl 记录里的 `cwd` 字段**：每个会话文件里带 `cwd` 的那条记录即该会话所属空间，`scripts/extract_flow.py` 的 `--list` / `--workspace` 分组全靠它，**不打开 `workbuddy.db`**。客户端界面另用 `~/.workbuddy/workbuddy.db` 的 `sessions.cwd` 分组（二者取值一致，db 可作交叉核对，见 `@references/storage-schema.md`） |
| **会话正文** | `~/.workbuddy/projects/<cwd 里的 "/" 全换成 "-">/<sessionUuid>.jsonl`，**一行一 JSON** |
| 会话运行态 | 同目录 `<uuid>.meta.json` |
| 文件回滚记录 | 同目录 `<uuid>.file-rollback.ndjson` |

> 路径映射示例：`/Users/you/Desktop/myproj` → `~/.workbuddy/projects/Users-you-Desktop-myproj/`

**注意：一个空间可能对应多个 project 目录**（路径前缀相同，例如带 `-2026-09-11-08-59-17` 后缀的）。某个空间的文件看着不全时，用 `ls ~/.workbuddy/projects/ | grep <关键词>` 找同前缀目录，逐个看时间范围。

### 4.2 记录类型（`type` 字段），共 6 种

`message` / `function_call` / `function_call_result` / `reasoning` / `file-history-snapshot` / `ai-title`

> **★ 最高频的坑：工具调用是 `function_call`，不是 `tool_call`。**
> 用 `tool_call` 过滤会得到 0 条，然后误判成「这个对话没产出任何文件」。

### 4.3 提问与回答长什么样

**提问**：`type=="message" && role=="user"` → `content[].type=="input_text"` → `text`。

但这个 `text` **外面套着巨大的上下文注入块**（身份文件、user_info、模式提醒……），真实提问只包在：

```html
<user_query>……真正的提问……</user_query>
```

**必须先正则剥壳**，否则会把几万字注入上下文当成用户提问。

**回答**：`type=="message" && role=="assistant"` → `content[].type=="output_text"`（也可能是 `"text"`）。一条回答常被拆成多个 block，需按时间顺序拼读。

### 4.4 ★ 产物怎么识别（本技能最关键的一步）

**不要靠回答文字里提到的文件名来统计产物**——回答会漏、会错、还会提到别的对话产出的文件。只认写文件调用：

```python
if d.get("type") == "function_call" and d.get("name") in ("Write", "Edit", "MultiEdit", "CreateFile"):
    args = json.loads(d.get("arguments") or "{}")
    path = args.get("file_path") or args.get("path") or ""
```

按**首次出现顺序去重**，得到「这个对话产出了哪些文件」。

## 五、输出格式

### 5.1 默认骨架（用户没特别要求时按这个走）

1. **总览节** —— 时间轴 + 关键数字 + 「这一阶段实际做完的几件事」
2. **逐对话节** —— 每段固定三段式：
   - **我问了什么**：原文**改编为结构化条目**（保留原意、追问顺序、硬性交付要求；**不要 1:1 照抄口语**）
   - **AI 怎么答**：**大幅精简**，只留结论 / 判据 / 可复用事实；**表格优先于段落**
   - **产物**：名字 + 类型 + 位置
3. **产物总表** —— 名字 / 来源对话 / 类型 / 完整路径
4. **沉淀结论节** —— 把反复验证过的判据抽出来，**脱离对话上下文也能单独用**
5. **未完结事项节** —— 显式留下没做完的事，避免下一阶段重新摸一遍
6. **归档说明节** —— 归档范围、例外文件及原因、原空间有没有被改动

### 5.2 计数口径必须写清

提问计数有三层，**写文档时只用去重后的口径，并在文末注明**：

| 口径 | 含义 |
|---|---|
| 原始条数 | 记录里 `role=="user"` 的消息总数（含重复注入） |
| 去重后 | 抹掉空白差异后相同 prompt 只算一次 |
| 实质提问 | 去重后再剔除「请继续执行任务」这类**辅助轮** |

> 真实偏差量级（实测）：原始 **43** 条 → 去重 **35** 条 → 实质提问 **32** 条。
> **直接用原始条数会虚高约 35%。** 做文档前先用 `manifest.json` 里的三个计数分别核对一遍，别混用口径。

### 5.3 需要文件交付时的样式约定

- **单文件 HTML、浅色主题、自包含 CSS**（不依赖外部资源）。
- 保留本系列的视觉系统：`--s` / `--e` / `--c` / `--a` 四色标签、`.sk` 卡片、`.callout` 提示块。
- **引用英文原文必须给三层：英文原文 → 中文翻译 → 中文解读。** 只有「原文 + 解读」不算完整。
- 用户偏好：**先给结论，再给结构化细节**；喜欢对比矩阵与 P0/P1/P2 分级。

## 六、防幻觉与判据分离（硬约束）

归纳文档天然带着「已经整理过」的可信感，一旦里面的归属或数字是编的，用户极难发现。**本节优先级高于上面所有格式要求。**

1. **产物归属只认记录，不认叙述。** 回答里提到某个文件名 ≠ 是这个对话产出的。一律回 `function_call` 的 `file_path` 求证。
2. **对不上的文件必须显式说明。** 目录里有、记录里没有的文件，写成「来源不在本次范围内，未纳入归档」，**不要顺手算进去**。
3. **数字必须交叉核对。** 提问数、产物数、文件数三处口径要自洽，且能与原始记录复算一致。
4. **原话与改写要分得清。** 提示词允许结构化改编，但**改的是形式不是意思**；硬性交付要求、追问顺序、否定过的方案不能改掉。
5. **产物归档一字不改。** 复制而不是改写；校验用 md5 / `diff -r`，**校验不通过就不算完成**。
6. **不确定就说不确定。** 时间范围、归属存疑的，写「存疑」并给出依据，不要抹平。

## 八、完成判据

一份合格的归纳交付物，**以下六条全过才算完成**：

1. **范围闭合** —— 目标空间与对话已指认清楚，没有「大概就这些」的含糊表述。
2. **骨架完整** —— 5.1 的六节都在，或缺节有明确理由。
3. **计数可复算** —— 提问数写在文档里，且口径已注明（去重后 / 含辅助轮）。
4. **产物可追溯** —— 每个产物都能指到具体对话，且来自记录的写文件调用。
5. **例外已说明** —— 对不上的文件、存疑的归属，都已显式写出。
6. **校验已通过** —— 归档文件 md5 / `diff -r` 一致；HTML 标签平衡校验无未闭合、无错位。

## 九、降级与边界

- **脚本跑不了时**（Python 缺失、路径异常）：不要退回「凭记忆写总结」。改成手工读 jsonl——用 `grep`/`head` 直接看记录，逐条核。**降级的是工具，不是判据。**
- **记录缺失或损坏时**：如实说明哪几个对话读不到，其余照常归纳。**不要用回答文字或用户描述去补写缺失对话的内容。**
- **只归档不总结时**：用户可能只要产物归位。这时**只做 Step 3–4**，不强行产文档，但仍要出「产物总表 + 归档说明」一份轻交付。
- **要「搬家」而非「归档」时**：不要动 `workbuddy.db` 去改 `sessions.cwd`——那会牵动云同步映射（`edge-sync-mapping-v4.db`），风险远大于收益。真要搬，先确认应用已完全退出、全量备份后再动手。
- **本技能不改变事实边界。** 它只改变**已经发生过的对话怎么被还原和呈现**，不改变对话本身。记录里没有的，就是没有。
- **语言**：默认简体中文输出；用户要求别的语言时跟随。
