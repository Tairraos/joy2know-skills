# harness 工程专家 · 晓得乐（joy2know-harness）

> 写代码的成本已经趋近于零，但大多数项目还是为人写的形态。

## 他解决什么问题

「智能体优先」喊了很久，落到项目上常见的是这样一幕：

- 规范写在文档里，没人执行，也没有机器在守；
- 知识活在聊天记录、会议纪要、某个人的脑子里 —— 下一个会话的智能体一个字也看不到；
- 想重构，但不知道动哪里安全、动完怎么证明没改坏;
- 项目接了一堆 CI，但没人说得清哪个平台要 build、发布走不走草稿；
- 攒了半年技术债，想一次性还清，越攒越不敢动。

他把这一环补上：**判定起点 → 逐阶段落地 → 把约束变成机器在守的东西 → 决策当场落盘。**

## 三条底线

1. **技术栈、目标平台、发布方式一律不猜。** 这三样不可从代码推断，不明就停下来问，问完写进仓库。
2. **改造路线，计划没被确认前不碰一行业务代码。** 用 `git diff --stat` 自证，扫描时发现的 bug 只登记不顺手修。
3. **施工图竣工必须拆解。** 一次性流程归档、长效契约迁移进常驻文档；自检没过就不许删 —— 近千行的僵尸文件比没有文件更糟。

## 他的两条路线（互斥，不许混用）

| 你在做什么 | 走哪条 | 第一动作 |
|---|---|---|
| 从零建一个新项目 | **新建路线** | 索取需求并复述确认 → 定技术栈 → Day 0 十项 → 阶段 A–G |
| 手上已有能跑的代码 | **改造路线** | 只做阶段 1：扫描 + 出计划（`git diff --stat` 自证没碰代码）→ 阶段 2–5 → 收官拆解 |

两份施工图**自包含**（理念、流程、验收标准、模板全文都在里面），执行时不需要访问任何外部链接。

## 包内容

```
joy2know-harness/
├── .codebuddy-plugin/plugin.json     核心配置
├── agents/joy2know-harness.md        角色定义（系统提示词）
├── avatars/expert.png                头像 512×512（由构建注入）
├── skills/joy2know-harness-rules/    内置技能（由构建注入）
│   ├── SKILL.md                      路由 / 纪律 / references 索引
│   └── references/
│       ├── new-project-harness-rules.md          新建项目全套规则（母本原文）
│       └── turn-project-to-harness-rules.md      存量改造全套规则（母本原文）
└── README.md
```

**施工图在 `skills/joy2know-harness-rules/references/`，与独立上架的技能包同源。**
角色定义只规定「什么时候走哪条、怎么问、怎么验收」。

> **形态说明**：上面的目录树是**构建后所得包的形态**。仓库里的**源包**只有
> `.codebuddy-plugin/plugin.json`、`agents/joy2know-harness.md`、`skills.json` 与 `README.md` ——
> `avatars/` 由构建从仓库根 `avatars/joy2know-harness.png` 注入；`skills/` 由构建按 `skills.json`
> 声明的名单复制**唯一真源**。

## 怎么用

| 你说 | 他做 |
|---|---|
| 帮我把这个项目做成 harness 工程化 | 先看项目 → 报出判定结论（新建还是改造）与依据 → 按对应路线开工 |
| 我这有个老项目，怎么让它变得智能体能放心改 | 只做阶段 1：扫描 → 改造计划 + 问题清单，**不碰业务代码**，等你确认 |
| 我要从零起一个新项目，Day 0 该交付什么 | 先索取需求 → 复述确认 → 技术栈结论五项 → Day 0 十项 |
| 只帮我加一下 CI | 先说清「局部落地会缺哪些护栏」，再逐条问你三问（要不要 CI / 哪些平台 / 发布方式） |
| 我这项目离 harness 化还差多远 | 扫描出差距清单与分批建议，**不落任何改动** |
