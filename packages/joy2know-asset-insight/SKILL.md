# 技能专家运营洞察

**一句话**：把平台「运营数据」页的数字，变成「所以呢？」的答案。

## 什么时候用它

| 用户说 | 你要做的 |
|---|---|
| 「看看运营数据」「最近表现怎么样」 | 拉数据 + 出**完整报告**（结论先行 → 排行 → 趋势 → 原因 → 建议） |
| 「哪个技能最火 / 谁用得最多」 | 只回答**排行 + 为什么**，不用铺全套 |
| 「为什么没人用」「留存怎么这么低」 | 拉数据后**重点做归因**，并区分「样本太小」与「真的没需求」 |
| 「上周改完有效果吗」 | 拉**两段窗口对比**（改前 / 改后），看调用与安装的斜率变化 |

## 数据从哪来（**纯接口，不必开浏览器**）

```bash
NODE=/Users/xiaole/.workbuddy/binaries/node/versions/22.22.2-6/bin/node
$NODE ~/.workbuddy/skills/开放平台发布/scripts/pub.mjs ops --top 20        # 控制台排行
$NODE ~/.workbuddy/skills/开放平台发布/scripts/pub.mjs ops --json          # 原始 JSON
$NODE scripts/ops.mjs --out <输出.html> [--days 30]                        # 本技能：出 HTML 报告
```

接口：`POST /api/v2/open-platform/asset-metrics/daily`
体：`{ assetIds:[…], metricTypes:[…], startTime:"YYYY-MM-DD", endTime:"YYYY-MM-DD" }`

### ⚠️ 三个必须知道的坑（都踩过）

1. **接口名不在常规清单里** —— 它是 `/asset-metrics/daily`，得从前端 `page-*.js` 里的
   `metricsPort.getAssetDailyMetrics` 才能挖到，**照 `/capabilities/*` 的规律猜会全是 404**。
2. **时间是 `"YYYY-MM-DD"` 字符串**，不是毫秒时间戳。传数字会报
   `请求体不是合法 JSON`（这个报错很有误导性 —— 明明 JSON 是合法结构）。
3. **`metricTypes` 只认 6 个值**：`installs` `calls` `activeUsers` `frequency`
   `weekRetention` `errorRate`。**塞进任何别的值，整个请求返回 `code 100001`**，
   而不是「忽略未知指标」。（试过 `hourlyCalls`，全军覆没。）

细节与字段结构见 @references/metrics.md。

## 五条指标怎么读

| 指标 | 含义 | 读法 |
|---|---|---|
| `installs` 安装量 | 装了多少次 | **入口热度**。只说明有人点进来，不代表在用 |
| `calls` 调用量 | 被调用多少次 | **主排序依据**。真正的使用强度 |
| `activeUsers` 活跃用户 | 去重人数 | 注意**各资产独立去重，跨资产相加会重复计人** |
| `frequency` 人均频次 | 每人用多少次 | **≥3 说明形成了习惯**；≈1 多半是「试一下就走」 |
| `weekRetention` 次周留存 | 下周还回来的人占比 | **最该盯的一条**。普遍为 0 = 拉新驱动，不是复访驱动 |
| `errorRate` 错误率 | 失败占比 | 本次实测**恒为 `na`**（平台未下发），别拿它下结论 |

## 四把尺子（分析框架）

拿到数据后**按顺序**过这四关，每关产出一句话结论：

1. **集中度** —— Top3 / Top5 占总量多少？
   **>70% 即头部集中**。含义：资源压头部，长尾别平均用力。
2. **粘性** —— 每安装被调用几次（`calls ÷ installs`）？
   比安装量更能反映真需求。**安装多、调用少 = 装了不用**，那是体验或引导的问题（数据只能指出位置，原因要去看流程）。
3. **留存** —— `weekRetention` 非零的有几个？
   若**全站几乎为 0**，说明问题不在「哪个资产」，而在「**首次使用没有钩子**」。
4. **加速** —— 近 7 天调用 ÷ 30 天调用。
   - **≥40%** → 近期在加速
   - **10%~40%** → 平稳
   - **<10%** → 热度已过去

## 报告长什么样

**先结论后细节**，七节固定结构：

```
一、结论先行      4 条，每条带数字，直接给判断（"Top3 吃掉 88%"而不是"排名前三的分别是"）
二、总览          4 个 KPI 卡 + 口径注
三、访问排行      全量表格（调用/安装/活跃/频次/有效天数/近7天占比）
四、平台趋势      日序列折线 + 安装柱（能看出拐点与增量来源）
五、原因分析      为什么头部赢 / 为什么长尾不动 + 粘性榜 + 加速榜
六、行动建议      3~5 条，每条可执行、指向具体资产
七、口径与限制    数据源 / 指标 / 缺口 / 未做维度
```

**硬要求**：
- 每条结论**必须带数字**，不接受"表现较好"这类空话；
- **样本太小的必须明说** —— 装 1 次、调 2 次的资产**不能据此判死刑**，
  要写「样本太小，需再观察」；
- **因果要克制** —— 数据能指出「谁装了不用」，**但看不出为什么**，
  不要编原因，要说「要去看首次使用流程」。

## 口径与边界

- **只返回有数据的资产**。全站 35 个、有数据 26 个，剩下 9 个（含当天刚提交的）
  **不在表内 ≠ 表现差**，报告里必须写明。
- **日序列有跳日**（平台只在有活动时落点），算「有效天数」用「调用 > 0 的天数」。
- **近 7 天 / 30 天 / 90 天**三档窗口都要拉 —— 单窗口看不出斜率。
- **不做**：来源渠道、地域、机型等维度（平台未开接口，别假装有）。
- **不碰凭证**：复用 `开放平台发布` 技能的凭证，失效时按它的提示引导用户重新登录。
