# 资产包维护

**包建好只是开始。** 这一环的坑几乎全是**静默的** ——
不报错、不告警，只是内容悄悄和真相不一致。

---

## 一、内嵌联动：升一个技能，必查「谁内嵌了它」

```bash
grep -rl "<技能名>" packages/*/skills.json packages/*/.codebuddy-plugin/plugin.json
```

### 为什么必须查

构建对「内嵌技能」列只做**实时读取、不拦版本不匹配** ——
会出现「清单显示嵌着新版、旧 zip 里其实是旧版」，且 **0 告警**。

### 两层过期（都要处理）

| 层 | 症状 | 怎么发现 |
|---|---|---|
| ① 包版本号没抬 | 内嵌方版本落后 | 对账工具（见「资产状态追踪」） |
| ② **agent 正文复述了旧规则** | **自检全绿，但团队照旧指令人做错事** | 自检**不看正文** —— 必须人工比对 |

第 ② 层最阴：`agents/*.md` 正文里往往抄写了被引用技能的规则条文，
技能改了规则而正文没跟 → 团队继续照旧指令人做错事，**自检全绿**。

### 收尾必做

```bash
unzip -p dist/<包>-v<版本>.zip <包>/skills/<技能>/SKILL.md | grep -m1 '^version:'
```

并 `diff` 内嵌的 reference / 脚本与源包 ——
**只比对版本号不够，内容也要比**。

## 二、派生信息两处 = 迟早漂移

**同一份信息写在两个地方，就等于制造一次未来的漂移。**

### 已由构建纳管的四列

`README.md` 资产总表：**状态 / 版本 / zip 体积 / 内嵌技能（版本）** ——
由 `build.mjs` 的 `syncReadmeTables()` 统一刷。

### 三条硬规矩

1. **纳管范围按「值从哪来」划，不按「上次谁出过错」划** —— 凡算得出来的格子都该一次纳管干净。
   实测「只纳管一列 = 没修」：只接状态列时，某包升 1.6.0 后 README 仍写 `1.3.0 / 35.2 KB`，
   且 **0 告警**。
2. **「跳过」必须报出声** —— 形状守卫（格子不像该列该有的样子就不改）必须把跳过项列出来，
   否则只是把「改错」换成「静默不改」。
3. **判定有没有漏列**：改一个包版本 → 跑构建 → 看输出点名了哪几列，**没出现的列就是没纳管**。

⚠️ **人工维护区的加总也别信上一轮写的数** —— 必须逐包数一遍。
**批改脚本必须报处理了几条。**

## 三、检测报告是漂移高发区

报告 `packages/<包名>/<包名>.md` **只进 git、不进 zip，构建对它一个字都不校验**。

→ 换头像、改 `displayName`、升级内嵌技能后，里面写死的数字
（zip 体积、源包体字节、头像规格、「头像仍是占位图」未覆盖项）**集体变假，且 0 告警**。

**改完包要按「变更 → 受影响位置」映射表反查**，别凭印象扫：

| 你改了什么 | 要同步的位置 |
|---|---|
| 抬版本号 | SKILL.md / plugin.json / 包内 README「## 版本」/ 报告头四行 / 正文引用 |
| 换头像 | `avatars/<名>.png` + **重跑构建**（专家/团图标在 zip 内）+ 报告的头像规格描述 |
| 改 `displayName` / `profession` | `plugin.json` + `agents/*.md`（两处成对）+ agent 的 `description` 开头 + README H1 + 检测报告 |
| 升级内嵌技能 | 内嵌方版本 + **agent 正文复述的规则条文** + 重建 zip |
| 改内容 | 报告第二节能力清单 + 第七节履历 |

⚠️ 构建会检查「报告是否比源码旧」（有文件比报告新就告警「报告可能已过期」）——
但这只比**时间戳**，不比**内容真假**。

## 四、头像三处同步

| 归属 | 放法 | 构建时去向 |
|---|---|---|
| 专家 / 团自身 | `avatars/<包名>.png` | 该包 `plugin.json` 的 `avatar` 所指路径（**在 zip 内**） |
| 团成员 | `avatars/<包名>/<文件名>.png` | 包的 `avatars/<文件名>`，须与 `members[].avatar` **逐字对应** |
| 技能 | `avatars/<技能名>.png` | 独立技能包**不注入**；被内嵌时复制为 `skills/<技能名>/icon.png` |

⭐ **换图后必须重跑构建** —— 否则传上去还是旧图。

⚠️ **一个技能图标超 500KB → 所有内嵌它的专家包全部打包失败**
（图标复制成 `skills/<技能名>/icon.png` 一起受校验）。
批量体检（一次扫完 `avatars/`）比逐个打包试错快得多。

⚠️ **量体积别把系统垃圾算进去**：`find … -not -name '.DS_Store'`。
用 `-exec cat {} +` 会把 `.DS_Store` 算进去（曾把一包源包体算高 6 KB），
而构建本来就排除它 —— **数字的出处要对，口径也要对**。

## 五、git 纪律

**一个资产包一条提交** —— 包是独立的上架单位，一条提交对应一个可交付物；
以后回溯某个包的某一版，`git log -- <包目录>` 直接给答案。

### 五段式注释

```
feat(skill|expert|team|fix|docs|chore): <动作> <中文名> · <包名> v<版本>

一句话定位。

设计要点：
- 这条包最不好自己悟出来的设计决定，2–4 条

包内文件（n）：
  <从磁盘枚举，不手写>

图标：avatars/<名>.png（512×512 PNG，nnn KB）
```

⚠️ **文件清单从磁盘枚举，不手写** —— 手写必然与实物不符。

### 非包文件各成一条

`feat(check)` / `docs(spec)` / `docs(readme)` / `chore(release)`；
**只改报告的包用 `docs(check)` 且不抬版本**。

### 批量提交三步

```bash
# 1) 每条提交准备一对文件：NN.paths（要 add 的路径，一行一个）与 NN.txt（五段式注释）
# 2) 用 --pathspec-from-file 喂路径 —— 不要用 $(cat ...) 展开
git add --pathspec-from-file=NN.paths
git commit -F NN.txt
# 3) 全部提交完统一验收：**提交前必做双向覆盖校验**（实际改动 ↔ 计划清单，两边集合必须相等）
```

改动列表要 `core.quotepath=false`（否则中文路径被转义成八进制）。

### 提交与构建的先后

- 先提交、后跑 `build --strict` 会多出一条「时间戳刷新」提交 —— **预期行为，不是漏提交**。
- 想少一条：**先构建再提交**。
- **验收之后不要再跑构建**，否则时间戳又变，工作区永远收不干净。

## 六、自检脚本（内嵌联动 + 派生漂移）

```bash
# 查谁内嵌了某技能 + 版本是否一致
python3 scripts/embedded.py --skill joy2know-musician --config-root .

# 反向自检
python3 scripts/embedded.py --selftest
```

**退出码**：0 = 无内嵌方或全部一致；1 = 有不一致；2 = 用法错。

## 七、本技能的边界

- **只管维护纪律**。字段取值 → 「资产字段规范」；检测报告怎么写 → 「资产包门禁」；
  驳回处置 → 「发布与驳回」；平台状态 → 「资产状态追踪」。
- **本技能讲的「派生信息两处」是原则，不是某个具体路径** ——
  目录结构由你的项目决定，照搬本仓库结构是「换个目录也能跑」的违反。
