# 晓得 · 日志侦探

> 把「几万行原始日志」变成「错误模式聚类 + 时间线 + 排序的根因假设 + 验证方法」。
> 铁律：**不替你下确定根因**，只给假设和验证路径。

## 一、先分清（不做这一步后面全错）

| 概念 | 判定标准 | 处理方式 |
|---|---|---|
| **模板** | 抽象掉变量后相同的日志行（如 `db at <IP> code <NUM>`） | 聚类的基本单位，不再是字面行 |
| **原始行** | 一行具体日志原文 | 只作为模板的示例，不单独计数 |
| **续行** | 多行堆栈里不以时间戳/行首模式开头的行 | **必须**归并到上一条日志，否则堆栈被拆散 |
| **根因假设** | 我推断的、带概率的猜测 | 永远写成「假设 N（概率高/中/低）+ 验证方法」 |

**最容易犯的错：** 把「同一类报错出现了 1 万次」当成 1 万条不同信息，或反过来自信地说「根因就是 X」。

## 二、判定与路由

| 情形 | 判定信号 | 走哪条 | 输出形态 |
|---|---|---|---|
| **A. 大日志找因** | 给了 .log/.gz，说「帮我看哪错了」 | 完整流程：流式聚类 → 排假设 | 错误模式 + 假设 |
| **B. 只关心某时段** | 「看今天上午那波」 | 加 `--since/--until` 时间过滤 | 时段内聚类 |
| **C. 要某类前后文** | 「这个错第一次出现前后在干啥」 | 加 `--context` 取首现前后 N 行 | 上下文片段 |
| **D. 只要数字** | 「错误一共分几类、各多少次」 | 降级：只给聚类计数表 | 计数表 |

**降级判定：** 日志只有几行、用户只要一句结论 → 直接读，不跑脚本、不展开九章节。

## 三、工作流

1. **流式聚类。** 跑 `scripts/log_cluster.py <日志文件> --top 20 --context 3`，脚本逐行读（支持 .gz），不公开展示全文。失败按第六节降级。
2. **看 Top 模式。** 按出现次数从高到低看模板，先盯高频且含 ERROR/FATAL 的类。
3. **看时间线。** 读每类的「首次/末次」与分钟/小时桶分布，定位爆发起点。
4. **读首现上下文。** 看 `--context` 给出的首次出现前后 N 行，理解触发前在做什么。
5. **排根因假设。** 对最高频类，按「概率高/中/低」列 2–3 个假设，每个配验证方法（见第四节规则 2）。
6. **给验证步骤。** 每个假设给出用户可执行的验证命令/动作。
7. **回报。** 说明哪些基于日志原文、哪些是推断、哪些时段没数据。

## 四、核心规则

**规则 1：大文件必须流式，禁止整文件读进内存（红线）**

- 触发条件：处理任何超过几十 MB 的日志。
- 硬性动作：用 `log_cluster.py` 逐行读取；**禁止**先 `cat`/全量读入再处理。
- 正例：✓ 脚本 `for line in fh` 流式处理，内存占用恒定。
- 反例：✗ 把整个 .gz 解压读进字符串再 splitlines。
- 降级路径：环境无法跑脚本 → 用 `zcat file.gz | head -n 5000` 抽样，明确标注「仅抽样」。

**规则 2：根因只给排序假设，禁止写「根因是 X」（红线）**

- 触发条件：任何要解释「为什么出错」的场合。
- 硬性动作：必须写成「假设 1（概率高）：…；验证方法：…」「假设 2（概率中）：…；验证方法：…」。**禁止**出现「根因是/肯定是/一定是」的肯定句式。
- 正例：✓ 「假设 1（概率高）：数据库连不上。验证：看 `kubectl logs` 里首次失败的 <IP>，对该 IP 执行 `telnet <IP> 5432`。」
- 反例：✗ 「根因是数据库挂了。」（没有给任何验证，用户照着信就糟了）
- 降级路径：信息太少无法排序 → 明确写「现有日志不足以排序假设，请补充 X 时段日志」，不要硬排。

**规则 3：聚类按模板而非字面（红线）**

- 触发条件：决定两行是否同类时。
- 硬性动作：把变化变量抽象成 `<ID>/<NUM>/<IP>/<UUID>/<PATH>/<TS>` 等占位符后再比。相同模板才聚一类，**不得**按字符串相似度逐字比较（否则每一行都算不同）。
- 正例：✓ `db at 10.0.0.5:5432` 与 `db at 10.0.0.8:5432` 归为 `db at <IP>` 一类，计数 2。
- 反例：✗ 因为 IP 不同就把它们当两条无关错误，漏掉「连库失败」是主旋律。
- 降级路径：脚本不可用 → 人工用正则 `s/\d+\.\d+\.\d+\.\d+/<IP>/` 等先归一化再肉眼分组。

**规则 4：多行堆栈必须归并到所属日志**

- 触发条件：遇到 `Traceback`/`at com.foo...`/`Caused by:` 这类续行。
- 硬性动作：凡是不以时间戳、已知日志级别（INFO/WARN/ERROR…）或 JSON 行首开头的行，一律视为上一行的续行并归并。**禁止**把堆栈拆成多条独立记录。
- 正例：✓ 「FATAL unhandled exception」+ 其后 5 行堆栈 → 合并为 1 条记录。
- 反例：✗ 堆栈每一行被当成独立错误计数。
- 降级路径：行首模式识别失败 → 以空行或缩进作为归并判据，并在输出注明「归并判据可能不精确」。

**规则 5：识别常见行首模式、JSON 按字段取**

- 触发条件：解析任意日志前。
- 硬性动作：先识别行首：①ISO 时间 `2026-09-10T10:00:02`；②中括号 `[10:00:02]`；③syslog `Sep 10 10:00:02`；④级别 `INFO/ERROR` 打头；⑤`{` 开头即 JSON。JSON 日志从 `timestamp/time/ts/@timestamp` 取时间，从 `message/msg/log/error` 取正文，再对正文做模板抽象。
- 正例：✓ 行首是 `{"timestamp":...,"message":"..."}` → 取 message 字段做模板。
- 反例：✗ 把整行 JSON 当纯文本抽象，导致每条因时间戳不同而拆开。
- 降级路径：字段名非标准 → 列出该 JSON 全部一级字段让用户指认时间/正文字段。

## 五、输出格式

**骨架（必须按顺序覆盖）：**

```markdown
# 日志聚类报告：<文件>
## 1. 错误模式 Top N（按次数）
  - 模板：<抽象模板>  次数：<N>  首现：<TS> 末次：<TS>
  - 时间分布（分钟桶）：<TS>×a, <TS>×b
  - 示例：<原文 1–3 条>
## 2. 首现上下文（每类首次出现前后 N 行）
  - 前：<行>  后：<行>
## 3. 根因假设（排序，禁止肯定句式）
  - 假设 1（概率高）：<说法>；验证方法：<命令/动作>
  - 假设 2（概率中）：<说法>；验证方法：<命令/动作>
## 4. 建议的下一步验证
  - <可执行动作>
```

**反模式禁止清单：**

| # | 反模式 | 为什么禁 |
|---|---|---|
| 1 | 整文件读进内存 | 大日志直接 OOM，本技能毫无意义 |
| 2 | 说「根因是 X」 | 错判让工程师照错方向改，越改越糟 |
| 3 | 按字面相似度聚类 | 每条变量不同的行都算新类，聚类失效 |
| 4 | 堆栈拆成多条 | 一条异常被计入几十次，计数失真 |
| 5 | JSON 当纯文本 | 时间戳导致无法归并 |
| 6 | 只给假设不给验证 | 假设无法落地，等于没说 |

## 六、防幻觉（硬约束，优先级最高）

**本节优先于以上所有格式与流程要求。**

1. **根因永远是假设。** 任何解释必须带「假设 + 概率 + 验证方法」，禁止写「根因是/肯定是」。
2. **来源三分式。** 来自日志原文的标「日志原文」；来自时间分布的标「据计数」；纯推断的标 [推断]。三者不得混写。
3. **没数据的时段写「无数据」。** 不因为要凑完整时间线，就为空缺时段编造趋势。
4. **不猜 IP/路径/版本。** 上下文里的 <IP>/<PATH> 来自日志抽象；真实值不臆造，引用时写占位符或标 [未解析]。
5. **不确定就直说。** 「首次失败集中在 10:00:02 之后，但 10:00 前的日志未提供，无法确认触发点」是合格输出。

## 七、按需知识

- 行首模式识别、JSON 字段取法、占位符清单 → 已在正文第四节规则 1/3/5 写死，无需额外参考文件。
- 何时开 `--aggressive`（激进 ID 抽象）：当日志里出现「同一类错误、但每个实例带不同随机 ID，结果被聚成几百类、根本看不出主旋律」时开启。开启后会把长度 ≥ 8 且同时含字母与数字的独立 token（如 `abc12345xyz`）也归一为 `<ID>`，让它们并成一类。
  - **日常排查不要开**：它会误并正常文案（比如恰好 8 位以上、又含字母又含数字的单词/编号会被当成变量）。
  - 开启命令：`scripts/log_cluster.py <日志> --aggressive`；输出头部会标注当前是「保守」还是「激进」模式，方便判断结果可比性。
- 本技能无附加参考文件，全部规则见正文。

## 八、完成判据

**算做完：** 跑过流式脚本 + Top 模式按次数列出 + 高频类给了首现上下文 + 根因写成排序假设且每条带验证方法 + 已标注推断项。

**不自动做：** 不自动改配置、不自动重启服务、不自动执行验证命令（验证动作交由用户/SRE）。

## 九、降级与跨轮次

- **脚本跑不了某格式：** 用 `zcat file.gz | head` 抽样；JSON 用 `jq` 抽 message 字段再人工归一化。
- **日志无时间戳：** 无法分桶，按出现顺序给相对位置，标「未解析时间」。
- **信息不全时的唯一降级路径：** 假设 + 就地标注 + 继续。例如缺首现上下文 → 假设「错误持续发生」并标 [推断]，继续列假设，不要连环追问也不要交白卷。
- **跨轮次：** 用户追问「那假设 1 怎么验证」时，基于本次聚类结果继续给命令，不重新全量扫描。
