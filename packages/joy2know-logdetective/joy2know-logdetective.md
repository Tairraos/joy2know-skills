- **规则是否自洽**：✅ 无互相打架。规则 1（流式）/ 3（模板聚类）/ 4（堆栈归并）/ 5（JSON 取字段）同向；
  脚本「只给聚类不给根因」与 §六 防幻觉硬约束一致。
- **推断是否标注为推断**：⚠️ 轻。时间桶/次数均为实测；但**「同一错误被不同时间戳格式拆成多类」**这一事实脚本不提示
  （详见六·局限 1），下游可能把 3 个类当成 3 种不同错误 —— 属于「未标推断」的信息损失，但非凭空编造。
- **错误提示是否可指导下一步**：✅ 缺失文件「错误：文件不存在 -> 路径」；空文件「未发现任何日志记录。」；
  `--top` 非数字 argparse 直接报 `invalid int value`。均「发生了什么 + 怎么办」，无裸堆栈。
- **边界是否优雅**：✅ 空文件 / 单行 / 超大行 / 非 UTF-8 / 无时间戳 / 中文无时间戳 / 目录当路径 全部不崩、不静默——
  非 UTF-8 用 `errors="ignore"` 吞掉，无时间戳标「未解析到时间」，降级路径清晰。
- **零依赖是否守住**：✅ 仅标准库（见一）；SKILL.md 虽未显式声明，代码侧无 import 外部包。
- **值来源是否可追溯**：✅ 时间来自行首提取（ISO/syslog/JSON 字段），变量被抽象为占位符；
  取不到时间显式标「未解析到时间」，未凭空补值。

**二审复核（对首轮结论的独立验证，第二轮补做）**

首轮把缺陷 1 表述为「`--since/--until` 对 ISO/bracket **完全失效**、全部记录被过滤、返回空报告」。
第二轮用**独立构造的最小样本**逐格复核，发现该表述**过宽**，已按实测结果改写（见第六节缺陷 1）。复核方法：

```bash
# 副本：cp -R packages/joy2know-logdetective /tmp/j2k-check/verify-log/pkg
printf '2026-09-23T10:00:00 ERROR db fail\n2026-09-23T12:00:00 ERROR db fail\n2026-09-24T11:00:00 INFO ok\n2026-09-25T11:00:00 INFO later\n' > t4.log
python3 pkg/scripts/log_cluster.py t4.log --until 2026-09-23T23:59:59   # → 未发现任何日志记录。(exit 1)  ❌
python3 pkg/scripts/log_cluster.py t4.log --until 2026-09-23           # → 未发现任何日志记录。(exit 1)  ❌ 纯日期上界同样坏
python3 pkg/scripts/log_cluster.py t4.log --since 2026-09-23T11:00:00  # → 9/23 10:00 未被剔除           ❌
python3 pkg/scripts/log_cluster.py t4.log --since 2026-09-24T00:00:00  # → 正确保留 9/24、9/25            ✅
python3 -c "print('2026-09-23T10:00:00' > '2026-09-23 23:59:59')"      # → True（'T'0x54 > ' '0x20，根因坐实）
```

**教训**：首轮只测了「跨日下界」这一种用法就下了「完全失效」的结论，属于**从单点失败外推到整条能力**。
两侧边界（`--since` / `--until`）、两种粒度（带时刻 / 纯日期）本应各测一格 —— 现在补齐后结论才准确。
**这条比缺陷本身更值得记**：断言的范围必须与实测的范围一致，否则报告会放大缺陷、误导修复优先级。

**一句话回答：本包的核心能力如果坏掉，是哪一步会亮红灯？**
→ 聚类/抽象/堆栈归并/JSON 抽字段坏掉，会在第二节对应用例出现**取值不符**（模板不抽象、堆栈被拆开）而非只报错；
`--until` 坏掉会在过滤后**返回空报告（exit 1）**亮红灯（已抓出）；`--since` 在边界日内失效则**不亮红灯**
（它只表现为「该剔的没剔」，输出看起来完全正常）—— 这正是缺陷 1 里更需要人工留意的一侧。
**但有一处不会亮红灯**：同一错误在 ISO/`[..]`/syslog 三种时间格式下被拆成 3 类（局限 1），下游看不到「合并总数」，
需人工意识到 —— 这是本轮抓出的真实盲区。

**已知缺陷**（**2026-09-23 已修** —— 修法与验收见本条末尾）：

- **【已修 2026-09-23】** **缺陷 1（中）· 时间过滤在「同一天边界」上失效：`--until` 会让上界日整天报废，`--since` 无法排除边界日内的早时刻。**

  **根因**（已定位到具体两处）：`extract_time`（`scripts/log_cluster.py:86`）对 ISO 行首返回 **`T` 分隔**的 `2026-09-23T10:00:00`；
  而 `parse_filter`（同文件 `:152`）把**参数**里的 `T` 换成**空格**成 `2026-09-23 23:59:59`；
  `in_range`（`:159`）用**字符串字典序**比较。两者第 11 位是 `'T'`(0x54) vs `' '`(0x20)，`'T' > ' '`，
  于是**任何与上界同日的记录都恒满足 `ts > until`**，被当作「晚于上界」剔除。

  **实测行为（两轮，均真跑；命令与结果见第五节「二审复核」）**：
  | 命令 | 应有行为 | 实际行为 | 判定 |
  |---|---|---|---|
  | `--until 2026-09-23T23:59:59`（数据含 9/23 10:00、9/23 12:00） | 保留 9/23 两行 | **`未发现任何日志记录。` exit 1** | ❌ 上界日整日报废 |
  | `--until 2026-09-23`（纯日期上界） | 保留 9/23 两行 | **`未发现任何日志记录。` exit 1** | ❌ 纯日期上界同样坏 |
  | `--since 2026-09-23T11:00:00`（应剔掉 9/23 10:00） | 剔掉 10:00，留下 12:00 起 | **9/23 10:00 仍在**（未被剔除） | ❌ 边界日内早时刻剔不掉 |
  | `--since 2026-09-24T00:00:00`（跨日下界） | 保留 9/24、9/25 | 保留 9/24、9/25 ✅ | ✅ **正确** |

  **准确结论**：**不是**「`--since/--until` 完全失效」——
  ① `--since` 在**跨日/粗粒度**用法下**工作正常**（上表第 4 行实测正确）；
  ② 真正的失效面是「**边界日的比较**」：`--until` 的上界日**整天报废**（纯日期上界也一样），
  `--since` 无法排除边界日内的早于某时刻的记录；
  ③ bracket 格式同理（`extract_time` 内部把空格转回 `T`，同样落入 `T` vs 空格）。
  因为实际用法中上界通常就是数据的最大日期，所以 `--until` 的症状表现为**整份报告为空**，看上去像「完全不能用」。

  这是 SKILL.md §二「情形 B」明确承诺的能力，对最主流的 ISO/bracket 日志在**上界方向**不可用。
  建议：`extract_time` 与 `parse_filter` 统一分隔符（都归一成 ` ` 或都保留 `T`）后再比较，
  并改为**逐行**过滤而非仅按「类首现时间」过滤。

  **旁证（同源的第二处不一致，建议一并修）**：过滤后保留行的「上下文」仍取自**原始全文**，
  所以 `--since 2026-09-24…` 的输出里，9/24 那类的「首次出现前 3 行上下文」会显示被过滤掉的 9/23 行。
  用户按时间过滤后仍看到窗口外的行，容易误判过滤没生效。建议上下文也按过滤后的行集截取。

  > **判定说明**：本轮**不将此条升为硬缺陷**——它不影响主流程（聚类/时间线/堆栈归并/JSON/流式全绿），
  > 且 `--since` 的常见粗粒度用法可用。若维护者认为「文档承诺的能力在上界方向坏掉」足够硬，可改判 `❌` 并优先修。
  > **但报告中「完全失效 / 全部被过滤」的原始表述已由第二轮独立复核推翻并修正**（见第五节）。

  **【已修 2026-09-23 · 版本 1.1.0 → 1.2.0】修法与验收**：
  - `parse_filter(dt_str, is_until=…)`：把 `--since`/`--until` 统一归一到 `YYYY-MM-DDTHH:MM:SS`
    —— 纯日期作**上界**补 `23:59:59`（上界日整天算在窗口内），作下界补 `00:00:00`。
    **两侧分隔符一致后字典序比较才有意义，这是修复「同日边界判错」的关键。**
  - 新增 `time_key()`：把任意时间戳（ISO / bracket / syslog）归一成同一个比较键；
    syslog 无年份 → 按**当前年**补全后再比较（只用于比较，**不改变输出里显示的时间戳原文**）。
  - `in_range()` 改用比较键；仍沿用「无法判定时间的记录默认保留」的原行为。
  - **过滤改为逐条记录生效** —— 原实现按「类首现时间」过滤，首现在窗口外的类会把
    窗口内的记录一并带走（用例 K 专门验证这点）。
  - `collect_context()` 接收时间窗口，窗口外的行**不再进入上下文**（即原「旁证」问题）。
  - 无法解析的时间条件 → **stderr 告警**（R1 降级必须留痕），不再静默当作「没有过滤」。
  - `SKILL.md` §二 补一句边界语义（纯日期上界含当天 / 逐条过滤 / syslog 补当年）。
  - **验收结果：12 组用例 12/12 通过**（纯日期与带时刻上界、同日与跨日下界、单日窗口、
    括号格式、syslog、逐行过滤、上下文隔离、无过滤回归、显示格式回归、非法条件告警）；
    **同一套用例对 git 原始版本只有 2/12 通过** —— 证明这组用例真的抓得住本缺陷，不是橡皮章。
- **缺陷 2（轻）· 实现有、文档无 ——【本轮未修】**（用户 2026-09-23 决定：本批不改「未文档化参数」）：脚本的 `--bucket`、`--no-context` 两个参数在 SKILL.md 任何位置均未出现（仅 `--top/--context/--since/--until/--aggressive` 被写）。门 2 兜底口径要求「实现里有的能力文档里必须写」。建议在 §三 工作流或 §七 补一句这两个开关的用途。
