# WorkBuddy 平台资产规范

> 本文件是**本仓库自带的完整规范手册**，内容搬自个人技能 `WorkBuddy资产包生产`
> （2026-09-23 固化）。目的：本仓库**不依赖任何本机技能目录** —— 换一台机器、
> 换一个 harness 克隆下来，照着本文件也能产出能过平台校验的包。
>
> 字段清单与体积规则来自本机实测 + 开放平台官方文档 + 官方模板包解剖。
> **平台规则会演进，正式提交前以后台实时提示为准。**
>
> 流程与门禁见仓库根 `AGENT.md`；字段校验的可执行版本是 `scripts/selfcheck.py`。

---

## 一、三种上传对象

| 类型 | 入口文件 | 上架后是什么 |
|---|---|---|
| **技能**（Skill） | `SKILL.md` | 技能市场里可被触发的能力 |
| **单专家**（Expert，`expertType: agent`） | `.codebuddy-plugin/plugin.json` | 专家市场里的一个人格 |
| **专家团**（Expert Team，`expertType: team`） | 同上，另加 `settings.json` + `setting.json` | 专家市场「专家团」Tab 下的一个团队 |

一个包**不能同时**是技能和专家（构建工具会报「类型有歧义」）。

## 二、技能包（Skill）

### 结构

```
{skill-name}/
├── SKILL.md              ★ 必须
├── references/           可选 —— 在 SKILL.md 里用 @references/xxx.md 引用
├── scripts/              可选 —— 由 AI 通过 Bash 执行
└── templates/            可选
```

根目录**只允许这四个子目录**（`scripts/selfcheck.py` 会报非白名单目录）。
根目录可以有多余文件（不影响解析），但**发布前检测报告这类开发期文档必须排除在 zip 外**
——`scripts/build.mjs` 已自动排除 `packages/<包名>/<包名>.md`。

> **最容易犯的错**：打包时多套一层 `skills/`，直接解析失败。zip 里第一层就必须是 `{skill-name}/`。

### SKILL.md frontmatter —— 9 个必填，一个都不能少

```yaml
---
name: kebab-case-name          # 仅小写字母、数字、连字符；须与目录名一致
display_name: 中文展示名         # ★ 官方字段表未列，缺了报解析失败
display_name_en: English Name  # ★ 官方字段表未列，缺了报解析失败
description: 用途 + 触发词 + 不适用范围    # 这就是分发渠道
description_zh: 简短中文介绍
description_en: A brief English introduction
category: writing              # ★ 官方字段表未列，缺了报解析失败
version: 1.0.0
author: 署名
---
```

**⚠️ 官方文档同一页里，字段表与 frontmatter 示例代码块不一致**：`display_name`、
`display_name_en`、`category` 这三个**表里没列、示例里有**。实测缺失会直接解析失败并点名报错。
**照字段表写必失败 —— 照示例写。**

**可选字段**：`allowed-tools`（逗号分隔白名单）、`disable-model-invocation: true`（只能手动调用）、
`user-invocable: false`（隐藏菜单）。

**已知 `category` 取值**：`writing`（官方示例值）、`search`、`capability`。取值不合规可在后台下拉里改，不影响功能。
（注意：这是**技能内部类型**，跟发布时的**市场类目**是两回事，见第九节。）

### `description` 是产品本身

- 技能靠 `description` 匹配触发，**`name` 不参与触发**。改 `name` 对触发零影响，改 `description` 才是改产品。
- 触发词要写全（含同义口语），并明确写**不适用于**什么 —— 后者能防误触发。
- **长度跟系列齐平（经验值，非平台硬限制）**：本系列实测 239–386 字，中位 348。
  新手容易一次写到 600+ 字（把「适用范围 + 不适用 + 触发词 + 边界」全塞进去），
  **超标近一倍会稀释触发权重**，也破坏系列一致性。写完横向量一遍，超了就压。
- **反直觉的取舍：`display_name` 越泛，`description` 越难压。** 名字宽（如「知识归纳」）
  而能力窄（只能读本机 WorkBuddy 会话）时，边界全靠 description 承担，字数必然膨胀。
  **遇到这种落差，先确认要不要改窄名字**（如改成「对话归纳」），比在 description 里堆边界划算。

### 脚本语言约定：首选 JS

- WorkBuddy **自带 Node 22 与 Python 3.13**，都不需要用户另装。技能里的 `scripts/` **一律首选 JS**
  —— 作者更擅长 JS、维护成本最低；**实在不行才写 Python**。
- 用 **`.mjs`**（显式 ES module），免去 `package.json` 的 `type` 字段，单文件即可跑：`node scripts/xxx.mjs`。
- **已存在的 Python 脚本不要为了「统一」而改写** —— 它们工作正常，重写只会引入新 bug。
- **需要第三方依赖时优先 pnpm**（`pnpm add <pkg>`，临时跑用 `pnpm dlx`）。
  不要 `npm install -g`，不要把包塞进用户的全局环境。
- 两个运行时都从 PATH 取（`node` / `python3`）；脚本入口要**先验依赖在不在**再干活，
  缺了给安装提示与降级路径（先例：`joy2know-storyboard` 先探 `ffmpeg`/`ffprobe`，缺了不崩而是降级）。

## 三、专家包（Expert / Expert Team）

### 结构

```
{expert-name}/
├── .codebuddy-plugin/plugin.json   ★ 必须
├── agents/*.md                     角色定义（1 个=单专家，N 个=专家团）
├── avatars/                        头像（数量与 agents 对应）
├── skills/                         内嵌技能（本仓库由构建时复制生成，源包里不放）
├── settings.json / setting.json    专家团必须（两个名字都要有）
└── README.md                       可选
```

专家包内**可以使用 `assets/` 目录**（实测有在架包这么用），比技能包宽松。

### plugin.json 全字段

```json
{
  "name": "package-name",
  "version": "1.0.0",
  "description": "英文描述（用于平台层）",
  "author": { "name": "署名" },
  "agents": ["./agents/xxx.md"],
  "skills": ["./skills/xxx"],
  "expertType": "agent",
  "agentName": "xxx",
  "displayName":   { "en": "...", "zh": "..." },
  "profession":    { "en": "...", "zh": "..." },
  "displayDescription": { "en": "...", "zh": "..." },
  "avatar": "avatars/expert.png",
  "categoryId": "06-ContentCreative",
  "defaultInitPrompt": { "zh": "...", "en": "..." },
  "plugin": "package-name",
  "tags": [ { "en": "...", "zh": "..." } ],
  "quickPrompts": [ { "en": "...", "zh": "..." } ]
}
```

### 平台硬约束（不满足会被打回）

| 约束 | 口径 |
|---|---|
| `displayDescription.zh` | **40–50 汉字**（官方口径，模板自己超标，自检按官方） |
| `defaultInitPrompt` | 必须与 `quickPrompts[0]` **逐字一致** |
| `tags` / `quickPrompts` | 固定各 **3 个** |
| `displayName` / `profession` / `displayDescription` | **必须中英成对** |
| `categoryId` | 必须命中官方「行业分类」**15 类**（见下），**专家与专家团共用同一份清单** |
| `avatar` | 必须是 `avatars/` 下的相对路径，且该文件为合法 PNG 512×512 / ≤500KB |
| `plugin` | 与 `name` 一致；`name` 与目录名一致 |

### `categoryId` 官方 15 类（`01`~`15`）

```
01-ProductDesign      产品设计      09-OperationsHR       运营人力
02-Engineering        技术工程      10-ProjectQuality     项目质量
03-GameSpatial        游戏空间      11-SecurityCompliance 法务安全
04-DataAI             数据智能      12-IndustryConsultant 行业顾问
05-MarketingGrowth    营销增长      13-TencentZone        腾讯专家
06-ContentCreative    内容创作      14-WorldWise          全球发展
07-SalesCommerce      销售商务      15-Education          教育
08-FinanceInvestment  金融投资
```

**⚠️ 不存在 `00-ExpertTeam` 这类「专家团专属分类」。** 曾把该值填进两个专家团包，
上传被平台直接打回：`categoryId "00-ExpertTeam" 不在合法分类列表中，请参考开发规范第八节`。
**专家团页面本身没有分类表**（清单在专家页，全平台共用）——别去专家团那页找清单，
找不到不等于不用管；两个团选同一类目是允许的。

### 专家团的三个专属要点

1. **根目录要同时放 `settings.json` 和 `setting.json`**（内容一致，一行：`{ "agent": "主理人name" }`）。
   平台校验器**实查 `settings.json`**（缺了报 `解析失败：settings.json 不存在或无法读取（Team 型专家必须在 plugin root 下提供 settings.json）`），
   而官方可下载模板 `trading-team.zip` 里用的是**无 s** 的 `setting.json`。
   **官方自己不一致，只放一个必挂；两个都放最稳**（各几十字节，无副作用）。
2. **主理人的 agent 文件名必须带专家团前缀**（如 `joy2know-cine-lead`），
   不可用通用 `team-lead`；成员 `name` 各不相同是正常的（官方 trading-team 同构）。
3. **`expertType: "team"` 时**另有 `teamInfo`（含 `leadAgent` 与 `memberAgents[]`）
   与 `members[]`（每个成员 `id`/`name`/`profession`/`avatar`/`role` 五个字段）。
   `agents[]` 的文件名去掉 `.md` 后须与 `members[].id` **严格一一对应**，
   **只有主理人**的 agent `name` 等于 `agentName`。

### 卡片上那个「名字」是 `profession`，不是 `displayName`

客户端实际渲染：**主标题 = `profession`，副标题 = `displayName`**
—— 与官方文档「displayName 是市场展示名称」的说法**相反**（客户端截图实证）。
想让卡片顶着「XX专家」这样的职业名，话就要写进 `profession`；
`displayName` 是**花名位**（可放人名或品牌署名）。**弄反了要重新提交审核。**

> 官方另有一句「Team 型 `profession` 须与 `displayName` 一致」，**实测不强制**
> （`joy2know-cine-team` 两者取值不同，仍正常上架）。留着这个预期即可——
> 万一哪天上传被卡，先把两者改成同一个值试。

### agent frontmatter

```yaml
---
name: xxx                    # 单专家须与 plugin.json 的 agentName 一致；专家团成员须等于 members[].id
description: 一句话说明
displayName:  { en: "...", zh: "..." }
profession:   { en: "...", zh: "..." }
maxTurns: 100
skills: [xxx]                # 引用内置技能名
---
```

**`maxTurns` 的配比是有意义的机制约束**：专家团里主理人给大（如 150）、成员给小（如 30）。
成员轮次少，就不会越权乱跑。

## 四、体积上限

| 对象 | 上限 | 谁会真的撑爆包 |
|---|---|---|
| 技能包 | **3 MB** | 二进制资源 |
| 专家 / 专家团包 | **20 MB** | 头像图片 |
| 单张头像 | **500 KB / 512×512** | — |

**纯文本 + 合规头像的完整包只有 100–600 KB**，离上限有 5–30 倍余量。
唯一的实操纪律：**头像压到 100–200 KB，二进制资源不进包。**

**尺寸不符只告警，体积超限才失败** —— 但注意连锁效应：
一个**技能**图标超限，会让**所有内嵌它的专家包**全部打包失败（图标会复制成
`skills/<技能名>/icon.png` 一起受 500KB 校验）。批量体检（一次扫完 `avatars/`）
比逐个打包试错快得多。

## 五、头像（图标）统一管理

### 三类，都在仓库根 `avatars/`，但去向不同

| 归属 | 放法 | 构建时去向 |
|---|---|---|
| **专家 / 专家团自身** | `avatars/<包名>.png` | 该包 `plugin.json` 的 `avatar` 字段所指路径 |
| **专家团成员** | `avatars/<包名>/<文件名>.png` | 包的 `avatars/<文件名>`，须与 `members[].avatar` **逐字对应** |
| **技能** | `avatars/<技能名>.png` | ① 独立技能包**不注入** ② 被内嵌时复制为 `skills/<技能名>/icon.png` |

**★ 关键事实：官方技能包里没有图标槽位。** 解剖官方 `find-skills` / `document-skills` /
`playwright-cli` 三个包，`plugin.json` 无 `icon` 字段、目录里无任何图片；官方专家包
（`design-engine`、`game-development-studio`）的内嵌技能目录同样没有图片。
**技能图标是后台发布技能时上传的平台侧资产，不进 zip。**
因此「技能图标要进包」只能靠给内嵌技能目录加 `skills/<技能名>/icon.png`
（这是超出官方结构的一层，构建工具有 `--no-skill-icons` 开关可关掉）。

### 处理用户自备头像

**先量规格，再决定处不处理 —— 多数情况原图直接可用。**

```bash
# macOS 自带，比解析字节稳
sips -g pixelWidth -g pixelHeight -g format -g hasAlpha <图路径>
```

三项判定：`512×512` + `PNG 或 JPG` + `≤500KB`。全过就 `cp` 覆盖，重新打包。

需要处理时才动 `sips`（零依赖、零积分）：

```bash
sips -c 512 512 --resampleHeightWidth 512 512 -s format png <源图> --out expert.png
```

> **坑：不要在 shell 里用字节常量断言 PNG 格式。**
> 曾用 `d[:8]==b'\x89PNG\r\n\x1a\n'` 在字符串里判断，因转义/比较问题把合规的
> 512×512 PNG 误报成「不是 PNG」。**改用 `sips -g format` 判定**；但**读宽高**用
> PNG offset 16/20 的 uint32 大端（宽在 16–23，位深 24，颜色类型 25）是可靠的，纯 JS 即可。

### 尺寸陷阱：生图工具默认吐 2048×2048

一次体检里 13 张不合规的图**全部**是 2048×2048 —— 不是个别疏忽，是工具的输出规格。
2048 的插画轻易 3–4 MB，**尺寸超了体积必然超**。但**缩到 512 就够，不需要牺牲画质**：
实测 2048×2048 / 3.8 MB → 512×512 / **334 KB 全彩 PNG**，连 256 色都不用降。
**看到图标超限，先看尺寸，别急着降质。**

### 缺图先摆占位图，别让构建门禁一直报错

先批量生成**规格达标**的占位图（512×512 / PNG / 几 KB），命名与真图一致。
这样构建门禁立刻全绿、清单能看清还差哪几张，人直接覆盖同名文件即可。

- 占位图要**一眼能认出是占位**（灰色相框 + 太阳 + 山形），不要拿真图配色糊弄。
- **占位图上印「谁 · 待替换」**：文件名只说得出 `polish-lead.png`，
  图上那句「闻山 / 主理人·总编审 · 待替换」才说得清该画谁 —— 一次要替换十几张时差别很大。
- **「还剩几张没换」不能靠文件名猜 —— 要记 sha1 台账**。替换是覆盖同名文件，
  路径与文件名都不变，光看文件在不在完全没用。生成时把 sha1 写进
  `avatars/.placeholders.json`（**该台账要入库**，它是真源），比对时拿当前哈希与台账比。
- **台账要覆盖「没入过账的图」**，否则统计会少算：没入台账的图（早期手工放的）会被静默跳过，
  实测输出「缺 0 · 占位 10 · 真图 5」三个数加起来 15 ≠ 总数 30。**加一条体积兜底**
  （占位图是几 KB 纯图形、真图基本 200KB 以上，取 40KB 作分界很宽）。
  改完**三类之和必须等于总数** —— 这是个该写进自检的断言。
- **顺手查「技能图标与专家自身头像撞图」**：一个专家内嵌某技能时，该技能图标会被复制成
  `skills/<技能名>/icon.png` 进同一个包；若当初图省事把专家头像同时当技能图标用，
  包内就会出现两张一模一样的图（实测 `joy2know-codebase.png` 与
  `joy2know-code-scholar.png` sha1 相同）。**体检时给 `avatars/` 全目录算一遍 sha1，列出重复组。**

**生成坑**：镂空圆角边框不能写成「外框覆盖度 − 内框覆盖度」并加 `if (a < 1.0)` 判断
——内部覆盖度正好是 1.0，减法被跳过，出来是实心块。**无条件相减再 clamp。**

### 头像内容的两条软约束（官方未强制，但值得守）

- **性别 / 身份不要凭画面猜。** 角色资产常有跨职业造型（戴帽压低发型的单马尾极易被误认成双马尾）。**只问，不猜。**
- 头像与 `profession`（卡面主标题，即用户认定的「名字」）语义要能对上。视觉形象与名称身份明显冲突时，**先问用户**，不要自行改名。

## 六、⚠️ 官方模板 ≠ 规范：模板里的取值必须回文档清单核

**已连续踩两次，同一个根因**：把官方可下载模板（`trading-team.zip`）里的**具体取值**
当成规范照抄，没回文档正文核。

| 第几次 | 照抄的取值 | 平台报错 | 文档里的真相 |
|---|---|---|---|
| 1（09-17） | 根文件名 `setting.json` | `解析失败：settings.json 不存在或无法读取` | 文档目录树写的是 **`settings.json`** |
| 2（09-18） | `categoryId: "00-ExpertTeam"` | `categoryId 不在合法分类列表中` | 文档「行业分类」共 **15 类 `01`~`15`**，无此类；模板实际用的是 `08-FinanceInvestment` |

**四条规矩**：

1. 模板能告诉你**目录结构和字段名**，**不能**告诉你**字段的合法取值域**。凡是有清单的字段
   （`categoryId`、`expertType`、`role`、`category`…），一律回文档正文的清单核。
2. **文档某页没有你要找的表，不代表不用管** —— 找不到就去相邻页找，别默认「这页没写 = 不适用」。
3. **平台报错里引的「第 N 节」是定位线索，先信它**，别以为是平台抽风。
4. **每修一个错误，必须同步在 `scripts/selfcheck.py` 里加一道门禁并做反向验证**
   —— 这两次都是平台先发现、本地自检一路绿灯。**门禁没盖到的字段，等于没有校验。**

## 七、上传前必须由人做的事

以下四件无法代劳，开工时就要说清，避免互相等：

1. **实名认证 + 人脸核身** —— 一个身份证全平台只能认证一个个人主体。**可全程并行，不要等产出。**
2. **头像风格拍板** —— 可以用 `scripts/make-avatar.py` 出稿，但配色要人定。
   多包同仓时头像集中在 `avatars/`，人只需覆盖文件、不用碰包。
3. **点「公开发布」** —— 不点只在本人账号下可见，**这一步最容易漏**。
4. **装回来跑验收** —— 审核通过只代表「能装」，不代表「能用」。

## 八、发布类目：技能要在后台选，专家随包提交

- **技能包内没有类目字段** —— 类目是发布时在**后台下拉框里选的**。选错会被打回：
  `所选类目与应用类目不符，请重新选择相符类目，至少应包含 ……`。
  「应用类目」是平台**按内容判定**出来的，「所选类目」是发布人手选的。**看平台给的提示照选，不要凭技能名猜。**
- 打回措辞是「**至少应包含**」，说明该项**可能允许多选** —— 命中项之外可再补一个近义类目，别只勾一个。
- **类目选错只影响审核，与包本身无关** —— 改类目重新提交即可，**不因为类目问题抬版本号**。
- **专家 / 专家团**：类目写在包内 `plugin.json` 的 `categoryId`，随包提交，发布页一般无需再选。
- 本仓库的逐包建议类目记录在 `release.config.json`，会自动汇总进仓库根的 `发布清单.md`。

## 九、许可与署名

### 写在哪 —— 仓库级三处，包内一个字不动

| 位置 | 写什么 | 为什么 |
|---|---|---|
| `LICENSE`（仓库根） | 许可协议**官方原文全文**（下载，别手写） | 有法律效力的是官方全文；自己写的摘要不是协议 |
| `package.json` | `"license": "CC-BY-4.0"`（SPDX 标识） | 工具链与 GitHub 能自动识别 |
| `README.md` | 「许可协议」一节：覆盖范围 / 允许 / 须遵守 / **署名格式模板** | 人看的入口；模板给出来别人才抄得对 |

**不改包内容**，两条理由：① Skill frontmatter 官方**没有 `license` 字段**，
硬塞有解析失败风险（同 `display_name` 那类坑）；② 包内**本来就有署名** ——
技能看 frontmatter `author`，专家/团看 `plugin.json` 的 `author.name`。
为一条说明去改包 = 抬版本 + 重打包 + 重传，不值当。

### 取原文，不要自己写

```bash
curl -sL -o ccby40.txt https://creativecommons.org/licenses/by/4.0/legalcode.txt
```

文件结构：**中文说明在前，英文法定文本在后，中间画分隔线，并写明「一切以英文法律文本为准」**。
中文段只做「说白了就是」的解释，不要假装它是译本。要引官方中文译本用 `legalcode.zh-Hans`，别自己译。

### 选哪个协议

- **以文档 / 提示词 / 图文为主**（技能包、专家人设、图标）→ **CC BY 4.0** 合适：
  允许商用与改编，**只要求署名**。与「作品集 + 获客入口」的定位一致。
- **纯代码仓** → CC 官方**不推荐**把 CC 协议用于软件，用 MIT / Apache-2.0。
  技能包里的 `scripts/` 是少量脚本、与文档一体分发，实践中 CC BY 仍可接受；介意可写双许可。
- 想禁商用 → BY-NC；要求衍生作品也开源 → BY-SA。
- **必须提前说清**：**BY 系列只保证署名，不保证别人不卖你的东西。**

### 署名格式（三行式）

```
原作：<中文名> / <英文名>（作者：<作者名>）
来源：<仓库地址>
许可：CC BY 4.0 — https://creativecommons.org/licenses/by/4.0/
```

**务必带一句「若作修改须注明」** —— CC BY 的署名义务包含「指明是否作出修改」，漏了这句模板是不完整的。

## 十、归置判断：这个技能该不该做成专家

每新增一个技能，**先过这一关**，给出结论和理由再动手，不要默默建包。

| 选项 | 什么时候选 | 成本 |
|---|---|---|
| ① 保持独立技能 | 它不从属于任何流水线，单独用最顺手 | 0 |
| ② 并进现有专家 | 与某个专家同线，扩一句 `profession` 即可 | 低（但要重传该专家） |
| ③ 新建单专家 | 自带完整人格与判断空间，**且能独立开场** | 1 包 + 1 图 |
| ④ 与别的技能组专家团 | 它天然是某条流水线的一环（有上游输入、有下游交付） | 1 包 + `settings.json` & `setting.json` + N 个 agent + N+1 张图 |

### 两条抓手（能挡掉大部分「其实不该做专家」的技能）

- **抓手一：输入从哪来。** 技能只能吃「别人产出的东西」＝**加工环节**，不适合做单专家
  ——用户点进去还得先粘一篇稿子，开箱体验很糟。能从一句需求**从零产出**的，才适合单专家。
- **抓手二：规矩松紧。** 「只改命中处、其余逐字保留」这类硬纪律能力，与人设鼓励的即兴发挥
  是**相冲**的。判定：**规矩钉得越死，越该做成团队里的一棒，而不是一个人格。**

### 专家团编排的四条经验

1. **先问「是不是固定流水线」。** 是 → 按阶段顺序编排（像视频生产：创意 → 分镜 → 提示词 → 后期，每阶段必走）。
   不是 → 主理人必须先做**诊断**再分派（像文案打磨：稿子的问题可能是结构／容量／形态／语气里的任意几个，
   全上会把稿子改成没人认得的样子）。诊断要有依据，**引原文作证**。
2. **工序顺序要能说出理由，不能只是「看着顺」。** 典型：把「去腔调」这类**减量、易改坏内容**的工序
   排在最后。理由要写进 agent 文件，至少三条：（a）它的规矩是「只改命中处」，先做再动结构等于白做；
   （b）**前序工序本身会引入同类问题**（重排结构时很自然写出「先说结论：」，正是要去掉的腔调）；
   （c）它是唯一可能改坏内容的工序，自带校验，必须作用在最终定稿上。
3. **相邻两棒的界线要写成硬规矩**，否则一定糊。做法：给每一棒写「只做什么、绝不做什么」，
   并且**用对方的活儿来解释**（例：「只挪位置、不改措辞、不删内容；改措辞归语言编辑，删内容归提炼编辑」）。
   跨工序的边界也要写（例：可视化产出的 HTML，文案交语言编辑，但**源码与标签不交**）。
4. **主理人的「严禁行为」必须写成可观测判定。** 光写「不许代写成员内容」没用；
   要写成「回复里出现『甲认为……乙建议……』这种一口气写多角色的内容即为违规」。

### 外部开源 skill 要不要「收进来」？先过三关

外部那些「给 Codex / Claude Code 装能力」的开源 skill，**不是选题，是执行层工具**。
先分两层：**自用层**（装给自己的 agent 用 → 不产生任何包）与**提炼层**（封装成 WorkBuddy 技能 → 才走归置判断）。
提炼前必过三关，任一不过就停：

| 关 | 判定 | 不过怎么办 |
|---|---|---|
| **许可关** | 仓库根有无 `LICENSE`。**没有 LICENSE ＝ 默认保留所有权利**，不能改编再分发、也不能照抄它的 SKILL.md 文字 | 直接排除。**上游软件自身的授权也要看** —— 工具免费不代表宿主产品免费 |
| **依赖关** | 引擎体积几十 MB~数百 MB，**装不进技能包（3MB 上限）** | 技能里只写「调用本地已装工具 + 安装指引 + 缺失时降级」，不打包引擎 |
| **输入关** | 它只能吃别人产出的东西 → **加工环节** | 做技能，**不做专家、不组团**。值得建团的线要 5~7 棒；只有 2~3 棒的做技能就够 |

补一条口径：**「合并进现有包」与「内嵌进现有包」是两回事。** 内容合进别人的技能里会污染它
已经写死的边界；而本仓库已有 `skills.json` 内嵌机制 —— **新技能保持独立可售，
同时被专家团内嵌**，两边的用户都够得着，且不产生副本。

### 多包并行的写作规范

批量生产系列包时，**先写一份系列写作规范**（统一九章骨架：先分清 → 判定路由 → 工作流 →
核心规则四件套 → 输出格式 → 防幻觉 → 按需知识 → 完成判据 → 降级），多个包分头生产，
风格才不会散。参考高星开源 Skill（如 zenstory-ai/drama-skills）时重点抄结构：
「按需知识路由表」「完成判据」「入口与边界」三段是通用精华。

## 十二、系列一致性硬规则（改包必过，逐条可查）

> **来源**：2026-09-23 全量检测（18 包四道门）暴露的**跨包系统性缺陷**。
> 这些不是某个包的问题 —— **14 个技能共用同一套骨架**（`四、核心规则` / `五、输出格式` / `六、防幻觉` /
> `七、按需知识` / `八、完成判据` / `九、降级与跨轮次`，标题逐字相同），同一类缺陷会在多个包**独立复现**。
> 所以改一个包时**先跑一次跨包审计**（见 R6），凡同类一并处置，不要改了这个漏了那个。

### R1 降级必须留痕（不允许静默）

脚本里任何「跳过 / 失败 / 丢弃 / 猜」都必须留下**可见痕迹**，三选一：
stderr 警告、返回结果里带标记字段、或非零退出码。

禁用形态：

- `subprocess.run(..., check=False)` 之后**不检查** `returncode`（失败静默）
- `except SomeError: pass` / `except: continue`（坏了但不说）
- 解析不出的条目**直接跳过且不计数**（用户以为「就这些」）
- **推断值当实测值用** —— 估算出来的字段必须显式标注（如 `duration_source: "inferred"`），
  不得与实测值同形输出

理由：**静默失效是本系列出现频率最高的缺陷类型**（2026-09-23 检测中 6 个含脚本包独立出现）。
用户拿到的是「看起来正常、但少了东西」的结果 —— 比直接报错更危险。

### R2 实现里有的能力，文档必须写

脚本的每个**用户可见**开关 / 参数，必须在 `SKILL.md` 里出现（通常落在工作流一节或输出格式一节）。

- 反例：`--bucket` / `--no-context` / `--max-depth` 实现了，但 `SKILL.md` 全文没有 → 模型不知道能这么用。
- 例外：纯内部 / 开发用开关（`--verbose` / `--seed` / `--rules` 这类）可以不写。
  **判定标准是「用户或模型会不会主动想用」**，不是「参数存不存在」。

### R3 同一规则只允许一种表述（口径唯一）

同一个路由、同一个数值、同一条判定，**不得在两处给出不同说法**。

- 反例：降级路由 D 在 §二 写「只给一句人话」，在 §九 写「一句人话 + 一条最可能的原因」→ 模型随机取一。
- 反例：同一条「60 秒口播版本」，一处写「不短于 40 字」，另一处自报语速 2 字/秒（60 秒 ≈ 120 字）
  → 两个下限差 3 倍，执行者无从取舍。

### R4 references 的「必做类」章节必须被 §七 路由点名

`SKILL.md` §七「按需知识」是模型找到 references 的**唯一入口**。references 里凡是**必做类**章节
（标题含：必跑 / 必做 / 自检 / 硬约束 / 禁止 / 翻车 / 纠正 / 坑 / 注意事项），
必须在 §七 的对应条目里被**点名**。

- 反例：`deck-patterns.md` 有「三、每页自检清单（生成后必跑）」，而 §七 只写「叙事结构模板与页数分配」
  → 模型读完这条不会去跑那道自检。
- 纯知识章（是什么 / 字段清单 / 参考表）不必逐章点名 —— **§七 是路由，不是目录**。

### R5 派生数值必须自洽可推

凡文档里**由其他声明推导得出的数值**（字数 = 语速 × 秒数、页数上限、分级数量、阈值），
必须能被文中的源声明推出来，不得自相矛盾。

- 反例：同一文档声明 2–3 字/秒，却只按 2 字/秒给出字数上限，把 3 字/秒那档漏掉。
- 做法：写完**当场算一遍**（秒数 × 语速区间 → 字数区间），把算得的区间写进文档。

### R6 同类缺陷必须全系列扫一遍

改完一个包，**必须**跑一次跨包审计，确认「同类问题在别的包是否存在」：

```bash
$V/bin/python scripts/series_audit.py .
```

- 它专查三类**可机器判定**的跨包缺陷：§七 路由覆盖（R4）、脚本参数未进文档（R2）、
  静默失败点初筛（R1）。
- **它报的是「候选」，不是判决** —— 概要章（「一、是什么」）、通用开关（`--verbose` 等）都会误报，
  必须逐条人工定性后再动手。
- 检测报告第六节要写明：「本轮扫了全系列，同类问题在 X 包也存在 / 不存在」。

### R7 已上线的包 `name` 冻结 · 改包名要同改 8 处

**来源**：2026-09-23 把 `joy2know-mr` 改成 `joy2know-articulate`（`mr` 是「先生」的角色意象，
单看包名看不出能力）。8 处全部改完、构建 0 告警、自检 11 项通过，**然后在平台上被驳回**：

> 包内 name "joy2know-articulate" 与当前资产的 name "joy2know-mr" 不一致：
> **name 是资产的唯一标识，不允许修改。** 请将 plugin.json 中的 name 改回 "joy2know-mr" 后重新打包上传

**① 一条硬结论（已实证，别再试）**：

- **`name` 是平台侧资产的唯一主键，已上线的包不许改。** 平台按 `name` 认资产 —— 改了就对不上，
  「更新」链路直接断掉，连重传都进不去。
- **`name` 用户看不到。** 卡片上显示的是 `profession`（如「晓得·表达条理与可视化专家」），
  本来就语义清晰；`name` 是纯机器主键。→ **改名的收益只落在仓库内部，代价是丢掉整条更新链路，不划算。**
- 想换标识只有一条路：**放弃该资产、以新名重新上架**（已上线状态与审核结果一起丢）。是否允许
  「删除后立刻用新名新建」**未验证**，也不建议为已上线的包去验证。
- **从未上线的包（`release.config.json` 里 `platform: null`）改名不受此限** —— 没有资产可对不上。

**② 改名要同改 8 处**（适用于未上线的包；已上线的包连改都不必改）：

| # | 位置 | 漏改的后果 |
|---|---|---|
| 1 | 目录 `packages/<包名>/` | 自检器按**目录名**校 `name`，报 `[XX]` |
| 2 | `plugin.json` 的 `name` | 同上；且平台侧标识与实际不符 |
| 3 | `plugin.json` 的 `agentName` | 自检校验 `agent name == agentName` |
| 4 | `plugin.json` 的 `agents[]` 路径 | 自检报「agents 路径 不存在」 |
| 5 | `plugin.json` 的 `plugin` | 与 `name` 不一致（三处应同值） |
| 6 | `agents/<包名>.md` 文件名 + frontmatter `name` | 同 4 |
| 7 | 检测报告 `packages/<包名>/<包名>.md` | 报告按「包根/包名.md」**精确路径**取，名字不对 = 构建判「缺报告」 |
| 8 | 图标 `avatars/<包名>.png` + `avatars/.placeholders.json` 台账 key | **不是告警是失败**：构建报「未找到自身图标」，该包上传必挂 |

另需同步的**外部引用**：`release.config.json` 的包键、`README.md` 资产总表与正文、
`发布清单.md`（自动区由构建重写，**「六、发布历史」不追改** —— 那记的是当时真实上传的文件名，
但**驳回/失败那一行要如实追加**）。

**③ 操作纪律**：

- **一律 `git mv`**，保住 git 历史为 `R` 而不是「删 + 增」；回退同样用 `git mv`。
- 改完依次做三件事：**全仓搜旧名**（**包括 `mr` 这类简称**，简称最容易漏）→
  `selfcheck.py <包>` 真跑 → **全量 `build`** 确认 zip 第一层目录名正确、0 告警。
- **内容零变化时不抬版本号**（与「类目被驳回、改类目重提不抬版本」同一口径），
  但在检测报告履历里**记一行改名清单**，让下一个人查得到。
- **动平台侧标识之前不要提交 git。** 本轮改名→被驳回→回退全程留在工作区，撤销是免费的；
  若先提交再试，回退就得多一轮 revert 提交。**「改标识」属高风险动作：先验证，再落库。**
